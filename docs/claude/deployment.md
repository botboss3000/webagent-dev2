# Deployment & runtime state guidance

Read this before touching deploy config, OAuth/secure-context code, or introducing any file the app writes at runtime.

## Shipping updated JS/CSS — the service-worker update path

The old development "unregister + clear-caches on every load" bypass has been **removed** (it caused reload thrash). The current, production-safe update path is:

1. **`sw.js` caches static assets stale-while-revalidate**, keyed by the `CACHE` constant (e.g. `webagent-v63`). On `activate` it deletes every cache whose name isn't the current `CACHE`.
2. **The backend serves `/sw.js` and all `/ui/*` + `/index.html` with `no-store`/`no-cache`** (`app/main.py`), so the browser's HTTP layer never pins a stale service worker or shell — the staleness only ever lives in the SW's own Cache API copy.
3. **`index.html` registers the worker and auto-reloads once when an updated worker takes control** — via both `controllerchange` and `updatefound → 'activated'`, guarded by `_hadController` (no reload on first-ever install) and a one-shot `_swReloaded` flag (can never loop). Navigation is network-first, so an ordinary reload always fetches the fresh `index.html` (and thus the latest registration script).

**To ship a frontend change: bump the `CACHE` constant in `sw.js`** (e.g. `webagent-v63 → webagent-v64`) in the same commit. That single byte change is what the browser's update check detects → the new worker installs (`skipWaiting`) → activates (`clients.claim`, drops old caches) → the page auto-reloads once on fresh code. Without the bump, an open tab keeps serving the previously cached JS/CSS until its next version change.

> **Do NOT re-add an unregister/clear-caches bypass block in `index.html`.** It fights the registration above and turns every load into unregister → re-register → controllerchange → reload — a thrash loop that resets the UI mid-interaction. If updates seem stale, the fix is almost always "bump `CACHE`", not a bypass.

## Production deployment

The app runs on a **Google Cloud Compute Engine VM** (project `webagent-495517`, instance `webagent-development`, zone `us-central1-a`, static external IP `34.69.22.204`). It is **not** on Cloud Run, despite the codebase being Cloud-Run-compatible.

**Public URL:** `https://webagent.live` (also `www.webagent.live`). Domain registered at Namecheap. DNS: two A records (`@` and `www`) → `34.69.22.204` via Namecheap BasicDNS.

**Stack on the VM:**

| Layer | What | Where |
|-------|------|-------|
| TLS / reverse proxy | **Caddy 2.x** with automatic Let's Encrypt | `/etc/caddy/Caddyfile` — `webagent.live, www.webagent.live { reverse_proxy localhost:8080 }` |
| App server | **uvicorn/gunicorn** running `app.main:app` bound to `127.0.0.1:8080` (loopback only — Caddy is the only public ingress). May run **multiple workers** (`uvicorn --workers N`, see Dockerfile). | systemd unit `/etc/systemd/system/webagent.service` |
| GCE firewall | `allow-http-https` rule opens tcp 80, 443 to `0.0.0.0/0`. Port 8080 is **not** exposed publicly. | Created from Cloud Shell, not from VM SSH (VM SA lacks compute scope) |

**Multi-worker correctness (two things to know).** The live chat WebSocket broadcast is **per-process in-memory** — with `--workers N` the browser's socket and the agent run often land on different workers, so live events don't reach the browser. This is handled by the **DB-tail reconcile** on the client (see README "DB is the source of truth"): cross-worker turns stream from the shared DB in ~1–2s chunks, same-worker turns stream smoothly over the WS. Single-worker gives the smoothest streaming; multi-worker is correct but leans on the reconcile. Second: the **singleton background loops** (scheduler, event runtime, ability pollers, watchdog, Remote Access, boot orphan-resume) must run in exactly one worker or automations double-fire and orphans re-ignite N times. `app/coordination/leader.py` elects one worker via a TTL'd lock row (`background_leader`) in the shared DB and runs them only there; if that worker dies another takes over within ~30s. No config needed — single-process always wins leadership instantly.

**Repo on VM:** `~/webagent` (user `botboss3000`). Python venv inside. Deploy via `git pull` on `main`. **All runtime databases live under `data/db/`** (`local.db`, `logs.db`, `recordings.db`, `vault.db`, optimizer scratch) and are gitignored — runtime artifacts, not tracked. The VM generates its own on first run. **Migration note:** older installs kept these in `app/db/`; on the first restart after this change the app **auto-relocates** any `app/db/*.db` into `data/db/` (only when the file isn't already there), so the VM keeps its data — **stop the server before deploying** so the DB files aren't locked during the move. Since both old and new locations are gitignored, neither blocks a `git pull`.

**Google OAuth:** redirect URI must match the public HTTPS URL → `https://webagent.live/api/v1/oauth/callback/google`. JS origin `https://webagent.live`. OAuth never works against `http://<vm-ip>:8080`.

**Secure-context APIs (`crypto.randomUUID`, `crypto.subtle`, clipboard, etc.)** require HTTPS or `localhost`. Plain `http://<ip>:8080` will throw `crypto.randomUUID is not a function` and break `bindDom()` in `ui/js/state.js`, leaving the agent WebSocket dot stuck on yellow (`Connecting...`). The polyfill in `ui/js/uuid.js` handles non-secure contexts — use `randomUUID()` from there, not `crypto.randomUUID()` directly. Any new secure-context API added to the UI needs a similar fallback or must be guarded behind a feature check.

**Status dots in the chat header:** green = WS subscribed (`agentWs.js` got the `subscribed` event); yellow = WS opening or no subscribe reply yet; red = WS closed or `currentUserId` missing. Yellow that never goes green almost always means a JS exception during init prevented `currentUserId` from being set, or the WS handshake never completed — check the browser console first.

  - **Left blank** (default) → nothing is written; the **first visitor** to the server's address sets the password via the setup page. On the cloud row the deploy log prints an explicit "open it now and claim it before anyone else" reminder (there's a race window on a public URL until you claim it — a deliberate, accepted trade-off).
  - **Filled in** → lands as **`BOOTSTRAP_ADMIN_PASSWORD=<pw>`** in the install's git-ignored `.env` (loaded at boot by `app/main.py` `load_dotenv`); the server self-creates the `admin` account on first boot, so it's claimed before the address is ever public and no setup page shows. On the **cloud** row the password is a **vault credential** (encrypted, auto-discarded after deploy with the cloud key) rendered in its **own slot above the cloud key** (deploy.js `_renderProvider` / `#ac-deploy-admin`, gathered as a `cred`), not the generic cloud-key list. On the **manual** rows it is embedded **in plain text** in the copy-paste command + QR (unavoidable for a one-liner install — the UI says so), and the setup script (`deploy/termux-setup.sh` / `windows-setup.ps1` / `macos-setup.sh`) writes it into `.env` from a `WA_ADMIN_PW` env var the command passes it (blank → no prefix at all). The password never persists (no config storage; vault-discarded on cloud). Those same setup scripts also honour a sibling **`WA_BOOTSTRAP_CODE`** env var (from the "Include this app's configuration" toggle — see "Setup bundle" front door #4): present → they write it to `bootstrap.json` for first-boot provisioning. Both env prefixes are built by `manual_common.env_prefix_posix` / `env_prefix_windows` (bare case byte-identical to the old admin-only prefix, so the browser's live mirror still matches).
  - Byte-mirror rule still applies: the manual command's admin prefix is built in BOTH `app/deploy/providers/*.py` `build_command` (via `manual_common.resolve_admin`) and `deploy.js` (`_mcResolveAdmin` + `_mcAdminPrefix*`) — keep them identical.

### Setup bundle — clone a whole install's config as one portable code

Beyond pre-setting just the admin password, an admin can package **this install's configuration** — its database connection, secrets-vault choice, and LLM provider + API key + preset model roster — into a single portable **setup code**, and apply it on a freshly-cloned install so the new box comes up already configured. Engine: `app/admin/bootstrap_bundle.py`.

- **Two code formats, one for each front door.** The Export/Import UI (below) uses **keyless `WABOOT2` codes** (`encrypt_code_open`/`decrypt_code_open`) — no password to type, since those endpoints already require a logged-in admin; a second shared secret would be friction, not security. These codes **never carry the admin login** (a real password can't be recovered from its stored hash without asking the admin to type it, and this path no longer does). The unauthenticated Setup page + boot-file paths still use the legacy **password-locked `WABOOT1` format** (`encrypt_code`/`decrypt_code`, PBKDF2-HMAC-SHA256 → Fernet) — there's no logged-in admin to gate on yet there, so the password still does double duty: it unlocks the bundle AND becomes the new install's admin login when an `admin` section is present.
- **It reuses the existing save paths** — it never invents a second way to store anything: `_persist_llm_config` (key → vault), `save_config` + `cred_store` (DB), `set_secrets_*` (vault), `register_user` (admin, apply-side only). Deliberately **not** a plugin (it reaches into core config), so it lives in `app/admin/`, not `plugins/`.
- **Four front doors:**
  1. **Export / import UI** — Data Settings → **Database → Data Migration** → **two expandable rows nested in that row's body** (`data-settings.html` `#ac-deploy-export-row` / `#ac-deploy-import-row`, wrapped in their own nested `.ac-list` beside the JSON data export/import) — MOVED here from the Deployment card (they're the current install's own config move, so they sit with the other backend migration tools). Reuse the shared expandable `.ac-row` / `.ac-ability-body` look. Head-expand is wired by `data-settings.js` `_wireDatabaseRows` (it walks every `.ac-row` in `#ac-database-card`, so the nested config rows are covered — they are NOT double-wired via `_wireBootRow` anymore); the Generate / Copy / Preview / Accept actions by `deploy.js` `_initBootRows` (handlers `_bootShare` / `_bootCopy` / `_bootPreview` / `_bootApply`), bound by id so the move needs no JS action change. **"Export config to link another account"** expands to the section checkboxes (AI model & key / Database / Secrets vault — no admin-login option) + a **Generate code** button that reveals the code and a **Copy** button immediately — no password, no QR. **"Import config to link this account"** expands to the paste box + a **Preview** button; previewing decodes the code and reveals a read-only summary of what it carries (with "already set" badges) plus an **Accept** button that adopts every carried section (**overwrite** — "link this account" means this box takes on the source's setup; confirm dialog is the safety net). Editing the code after a Preview hides the stale result so it must be re-previewed. Admin endpoints: `/admin/storage/bootstrap/{export,preview,apply}` (all admin-gated; none take a password anymore). This **folded in the old per-row DB "Share (QR)" / "Paste Config"** (removed from the Application Data row — the database is now just one section of the bundle).
  2. **Setup page** (`ui/setup.html` → `/api/v1/auth/setup-bundle`) — an optional "I have a setup code" reveal; on a fresh install the typed password decrypts a `WABOOT1` bundle, provisions everything (activating the DB), and logs straight in. Same one-time `admin_exists()` gate as `setup_admin`. (A `WABOOT2` code from the Export UI can also be pasted here — `decode_bundle` detects the prefix and needs no password for it — but it never carries a login, so `setup_bundle` still creates the admin from the password the visitor typed on this page.)
  3. **Boot file** — a `bootstrap.json` dropped next to the clone (repo root or `data/`), read at startup by `apply_boot_file()` (called in `app.main:startup`, before the security + LLM-from-env seeds). It may be a plaintext bundle or an encrypted `WABOOT1…` code (decrypted with `BOOTSTRAP_ADMIN_PASSWORD`, the same env var that presets the admin). Freshness gate = "no LLM configured yet" (NOT `admin_exists()`, because the env password creates the admin at import time). After applying it renames the file to `bootstrap.applied.json` so it never re-fires and the plaintext key stops sitting on disk (the vault copy is durable). `bootstrap.json` / `.applied.json` are gitignored; `bootstrap.example.json` is the committed blank template.
  4. **Deploy embed ("Include this app's configuration").** The Deploy panel's Repo-details has a **Bare install / Include this app's configuration** toggle (`#ac-deploy-embed-mode`) above the Activate button; picking *Include* reveals AI-model/vault/database section boxes (`[data-embed-sec]`). On deploy the app gathers those sections into a **keyless `WABOOT2` code** (`app/admin/bootstrap_bundle.export_code`, driven by the shared helper `app/deploy/config_embed.build_embed_code`) and writes that code onto the new box as `bootstrap.json` — so this is really front door #3 with the file placed *for* you. **Including config is DECOUPLED from the admin password (changed 2026-07-03).** It used to lock the bundle into a `WABOOT1` code with the deploy's pre-set admin password and so *required* a 6+char password — but that lock bought nothing (the bundle and its key always travel together to the same trusted new box: on a manual install the password already rides the same command in plaintext; on a cloud VM both land in the same box), and it wrongly *blocked* including config whenever no password was set. Now the bundle is keyless and the admin password does only its own job (pre-setting the first admin via `BOOTSTRAP_ADMIN_PASSWORD`); the two are independent — you can include config with or without a password, and `apply_boot_file` decodes a `WABOOT2` `bootstrap.json` with no password (it still accepts a legacy password-locked `WABOOT1` file for hand-authored bundles). A warning now only appears when the include is genuinely empty (no data in the ticked sections). **Cloud** targets: the manager (`run_deploy`) computes the code and injects `config["_bootstrap_code"]`, which `google_vm`/`ssh_vm` pass to `build_install_script(bootstrap_code=…)` (writes the `bootstrap.json` heredoc). **Manual** targets: the code rides the copy-paste command as a `WA_BOOTSTRAP_CODE='…'` env assignment (built server-side — the browser has no access to the secrets, so with Include on the row **fetches** its command from `/admin/deploy/command` instead of building it live, and hides the QR since a bundle is too big for one); the setup scripts write it to `bootstrap.json`. Sub-caveats: **database = SHARED** (the section is the connection, so the new box points at *this* app's DB, not a copy); a **remote vault's own access token is not exported** (re-enter it once on the new box — same limitation as the Export UI). **Admin login comes with the shared database — no carry (changed 2026-07-04).** Logins now live in the shared database's central `user_accounts` table (`app/auth/users.py`, DB-backed + pinned to the authority DB via `router.py` CONTROL_METHODS), NOT a per-box file. So a shared-DB deploy needs to carry *nothing* for auth: once the `database` section activates on first boot, `admin_exists()` reads the shared table and the box boots straight past setup with the exact same admin. The bundle therefore carries no `admin` section (`gather_bundle` never gathers one for the deploy path; only a hand-authored `bootstrap.json` may include a plaintext `admin` section, applied by `_apply_admin`). The Deploy panel still **greys out the "Admin password" field** once "Database (shared)" is ticked (`deploy.js _syncSharedDbLocks`; `_readSharedRepo` sends a blank password so no redundant `BOOTSTRAP_ADMIN_PASSWORD` is set — the shared DB already supplies the admin, so there's nothing to pre-set) — and greys (but keeps ticked) the **"AI model & key"** box, since the key is likewise reachable via the shared DB and the backend strips only the genuinely-redundant key itself. A fresh-DB deploy (database unticked) gets its own empty `user_accounts` and still honours the optional pre-set password to create that first admin. **LLM keys are omitted from the bundle when they're already reachable** — i.e. when the `database` section is included AND this host runs the default `inline_db` vault (`config_embed._llm_keys_resolvable_from_shared_infra` → `export_code(strip_llm_secrets=True)`). Rationale: the encrypted LLM key lives in the DB (`auth_elements.secret_ref`) and, for inline_db, so does the KEK/DEK that decrypts it (`app/encryption/vault_keys`), so a box on the shared DB resolves the key on boot with nothing extra — re-shipping the plaintext key would be redundant. The LLM section still carries provider/model/roster; only the keys are stripped. Every other vault mode (remote token not bundled; os_keyring/env keys are device-local) keeps the keys in the bundle so those deploys still boot working. **The JWT login-signing secret is shared through the vault, not carried (added 2026-07-04).** The HS256 signing key (`app/auth/jwt.py`) is per-box (`data/config/jwt_secret.txt`), so a fresh deploy/redeploy used to invent its own key and silently 401 every login pass a browser already held — the user *looks* signed in (the shell + unauthenticated GETs render) but every authed request is rejected, so **no agents and no Admin Tools appear** even though the shared DB and `is_admin` are correct. `ensure_shared_jwt_secret()` (in `jwt.py`, run at startup from `app/main.py` right after the account bootstrap, once the vault is active) reconciles this box onto ONE key kept in the shared vault (`get_secrets()` key `jwt_signing_secret`): adopt the vault's value if present, else publish this box's so later instances/redeploys reuse it. Because the deploy already configures the shared vault, the key effectively travels with it — every instance converges and tokens minted anywhere validate everywhere. A pinned `JWT_SECRET` env is respected (operator owns sharing then); the reconcile is best-effort so a vault hiccup never blocks startup. Frontend safety net (`ui/shared/js/auth-refresh.js`): a *cascade* of refresh-failed 401s — not only an `exp`-expired token — now trips the clean auto-sign-out → sign-in form, so a pass orphaned by an old key self-corrects instead of stranding the user in the powerless-zombie state.
- **Shared install recipe.** Every fresh-VM target injects the SAME bootstrap (`app/deploy/bootstrap.py`) — install git + Caddy + build prerequisites on Ubuntu 24.04, provision an isolated uv-managed Python 3.14, clone the chosen repo/branch into `/opt/webagent`, build a venv, write a minimal `.env` (+ an optional `bootstrap.json` when configuration was embedded — see "Setup bundle" front door #4), install the systemd unit, start the app service. It then installs the **Server Manager TUI** into its own Python 3.14 venv (`/opt/webagent/TUI/.venv`) and writes `/usr/local/bin/webagent` (with `WEBAGENT_TUI_NO_SUPERVISE=1` baked in, so it never auto-starts/keep-alives a SECOND server) — an admin who SSHes into the box can run `webagent` to inspect/restart/diagnose; this step is wrapped so a hiccup never blocks the deploy. Handed to the box as the cloud "startup-script" for `google_vm`, or **uploaded + run over SSH for an existing box** by `ssh_vm` (which then tails the recipe's `/var/log/webagent-bootstrap.log` for its live log). Docker uses the repo's Python 3.14 `Dockerfile` instead.
  - **The dependency install is FORGIVING — one optional wheel must not sink the whole deploy.** The old recipe ran a single `pip install -r requirements.txt` under `set -e`, so ANY one package failing (most often the optional `sqlcipher3-binary` at-rest-encryption engine, or a transient network blip on any of ~30 wheels) aborted the entire bootstrap and the app never started — even though the server runs fine without that optional package. Now it installs best-effort: try the full manifest; on failure fall back to the lighter `req_no_playwright.txt`, then guarantee the non-negotiable core (fastapi/uvicorn/pydantic/httpx/openai/jose/bcrypt/tiktoken/numpy/Pillow/tzdata/psycopg/asyncpg) so the server can always boot. **Playwright browsers are installed properly too** (best-effort `playwright install-deps chromium` as root + `playwright install chromium` as the app user) so browser automation actually works on the box — previously only the pip package went in, never the browser binary.
  - **The recipe PROVES the app answers before reporting success.** After starting the service it polls `http://127.0.0.1:$PORT/` for ~2 minutes; if the app never answers (e.g. it crash-loops on a bad import) it prints the recent `journalctl` and deliberately trips the `ERR` trap → the honest error page + a non-zero exit, so a broken install shows as "didn't finish" instead of a false "complete". Only on a real answer does it print the `WebAgent bootstrap complete` marker `ssh_vm` watches for.
  - **Bug fixed: a pre-set admin password used to break the whole script.** The recipe's `__ENV_BODY__` placeholder was also present *inside a source comment*; the renderer replaces every occurrence, so a two-line env body (port + `BOOTSTRAP_ADMIN_PASSWORD`) split that comment and left a stray uncommented shell line → a bash syntax error that killed every deploy where an admin password was pre-set. The comment no longer contains the literal token (guard note added in `bootstrap.py`).
  - **Caddy is configured FIRST, before the slow dependency install** (auto-HTTPS for a domain, else plain `:80`). The apt package starts Caddy on its default "Congratulations, configure me" **welcome page** the instant it installs; left until the end of a multi-minute pip install, that welcome page is all a visitor sees the whole time — and *forever* if a later step fails. So the bootstrap writes the reverse-proxy Caddyfile immediately, with a `handle_errors` fallback that serves a friendly **"installing…" holding page** (`/var/www/webagent-status/index.html`, auto-refreshing) whenever the backend isn't answering. The holding page turns into the real app the moment uvicorn comes up; a `set -e` **`ERR` trap** rewrites it to a clear "install didn't finish — read `/var/log/webagent-bootstrap.log`" page on any failure. The misleading Caddy welcome page is never shown.
  - **The holding page shows real, live install progress — not just a spinner.** The recipe writes `/var/www/webagent-status/webagent-status.json` (`{step, total, label, detail}`) via a `next_step`/`set_detail` bash helper at every stage (13 total: prepping the box, apt packages, Caddy, cloning the repo, the venv, Python dependencies, Playwright, writing config, the systemd unit, starting the app, the Server Manager TUI). During the dependency-install stage specifically, pip's own `Collecting <pkg>` lines are streamed into `detail` (via `PIPESTATUS`, so the fallback-on-failure logic still works), so the page names the actual package installing right now. The Caddyfile's `handle_errors` block carries a `not path /webagent-status.json` matcher so that ONE path is served as-is instead of being force-rewritten to `index.html` like everything else; the page's own JS polls it every 3s and renders a progress bar + current step + detail line. This is separate from the in-app Deploy panel's own live NDJSON log (which tails the same `/var/log/webagent-bootstrap.log`) — this progress feed is for someone who navigates straight to the VM's IP/domain during install.
- **`google_vm` needs no new Python dependency** — it drives the Compute Engine REST API with `httpx`, authenticating with the service-account JSON via the same JWT-bearer token exchange the Google Cloud Scheduler provider uses (`cryptography` signs the JWT). It ensures a `webagent-allow-http-https` firewall rule (tag `webagent-http`), creates the instance, polls the zone operation, and reports the external IP. Tear-down deletes the instance.
  - **It now VERIFIES the app comes up (was blind before).** The old flow returned `state:"installing"` the instant the create-VM API call returned, having checked nothing — so a bootstrap that later failed still showed a green "Deployed". After reading the IP it now polls `http://<ip>/` for up to ~10 min (`_poll_app_health`), distinguishing the three states via markers the bootstrap embeds in its status pages: `WEBAGENT-HOLDING` (still installing → keep waiting), `WEBAGENT-INSTALL-FAILED` (the box's `ERR` trap fired → **`state:"failed"`, `ok:false`** so the cloud key is kept for tear-down and no "live" deployment is stamped), else a real response → `state:"running"`. A timeout stays the honest `state:"installing"`. **Only the raw-IP path is polled** — with a custom domain Caddy serves over HTTPS on the domain and needs the admin's DNS first, so there's nothing to poll yet (the "point your DNS" messaging stays).
- **Ephemeral cloud keys.** The key is a secret → it goes into the encrypted vault (`app/deploy/credentials.py`, admin scope, service `deploy_cred:<id>`), never into `deploy.json`, never returned to the browser. On a **successful** deploy it is **auto-discarded** from the vault (the per-target "Forget keys after deploy" setting, default on), so the app holds no standing cloud access; tearing down later re-asks for the key. Non-secret settings live in `data/config/deploy.json`.
- **The sign-in "id" fields (and the Zone) travel with a shared vault DB.** The non-secret cloud setup is not a secret, so it stays in `deploy.json` as the local working copy — but it is ALSO mirrored into the vault in its OWN persistent row (service `deploy_connect:<id>`, `read_connect`/`save_connect`/`forget_connect` in `credentials.py`). What gets mirrored is `manager._mirror_keys(p)` = the target's `connect_config_keys` (the Google **project id**) **plus** any `shared_config_keys` (google_vm adds **`zone`**) — the split matters: the connect keys are the sign-in identity (they render in the Cloud VMs sign-in form and drive the "connected" check), whereas `shared_config_keys` ride along in the vault WITHOUT cluttering the sign-in form. Because this is a separate row from `deploy_cred:<id>`, the after-deploy key-forget leaves the project id + zone intact (only the key is discarded). Every save path (the Cloud VMs sign-in → `manager.save_connection`, and the Deploy card's Save → `manager.save_config`, which the `POST /admin/deploy/config` endpoint now routes through) writes them; every read path assembles config through `manager._load_config` (defaults → vault shared keys → local `deploy.json` on top), so a SECOND device signed into the same shared vault DB inherits the whole cloud setup (project id + zone + key) and can deploy without re-entering anything. "Remove account" (`disconnect(forget_config=True)`) drops the whole vault mirror row, so the account fully leaves the shared vault (the local clear stays narrow — only the sign-in id, leaving harmless settings like zone/repo in `deploy.json`).
- **Reusable GitHub key (private-repo cloning).** The Repo-details bar auto-detects public/private by asking GitHub (`POST /admin/deploy/probe-repo`); GitHub answers 404 identically for a private repo AND a wrong URL, so "not public" is only ever *unknown → add a token*, never a confirmed "private". A pasted token can be **saved once** into the same encrypted vault (`app/deploy/credentials.py`, service `deploy_github_token`, `save/get/clear_github_token` + `github_token_status`; endpoints `GET/POST /admin/deploy/github-token` + `/github-token/clear`). Unlike the per-target cloud key this one is **NOT** auto-discarded — it's the standing key the whole section falls back to when the token field is blank: the probe, the manual command builder (`_build_manual_command`), and every cloud target (via the `github_fallback` in `credentials.read` — OFF in `save` so it's never copied into a provider's own row). **The Source Control page's own shared token now uses THIS SAME vault key (changed 2026-07-04)** — `app/api/github.py` `_prime_shared_token_from_vault` / `_save_shared_token` read & write `deploy_github_token`, so the Git page and the Deploy panel share one durable, cross-device token (a device signed into the same vault inherits it; the git-page `token-status`/push/pull prime it, and startup migrates a legacy plaintext `provider.json` token into the vault once). `provider.json` is kept only as a plaintext local mirror/fallback for the synchronous git fast-path; `git_repos._shared_token()` prefers the vault-primed override. Still distinct from the production-mirror vault key (`app/production_mirror.py`, scoped to the *production* repo). The visibility the backend records is derived from the probe verdict client-side (`deploy.js _lastProbe`), not from the token field being non-empty.
  - **The vault row ALSO stores the repo URL (changed 2026-07-04).** The `deploy_github_token` row's non-secret `config` now carries `repo_url` — the CLEAN address of the repo the Source Control page tracks (`credentials.get/save_github_repo_url`; the git page mirrors its built-in `origin` there on prime/save/URL-edit via `github._save_repo_url_to_vault`). So a device — or a new deployment — signed into the same vault gets the repo **URL + token stored SEPARATELY** (never a tokenized URL). `manager.build_catalog`'s `shared_repo` falls back to this vaulted URL when the device has no local `_repo` slot, so the New-deployment Repo-details bar pre-fills.
  - **Deployed boxes get a CLEAN git `origin` (fixed 2026-07-04).** Previously the install cloned with the tokenized `clone_url` (`https://github_pat_…@github.com/…` from `manual_common.resolve_clone`), leaving the new box's `origin` — and the PAT — persisted in its `.git/config` (and printed to the install log). Now `resolve_clone` also returns `clean_url` (no token); `build_install_script(repo_url=<clone_url>, origin_url=<clean_url>)` clones with the token but then `git remote set-url origin "$ORIGIN_URL"` resets the remote to the clean address, and the "Cloning" status/log line shows `$ORIGIN_URL` so the token never lands in `/var/log/webagent-bootstrap.log`. The box authenticates future fetch/push with the token from its OWN vault (present when it shares the vault; else re-entered on its Source Control page). Wired through `google_vm`/`ssh_vm` (cloud); the manual copy-paste providers still embed the token in their one-liner since a manually-installed box may have no vault to fall back to.
- **Admin-only + confirm-gated.** All `/admin/deploy/*` endpoints (`app/api/deploy.py`), including the manual `command` builder, resolve the caller via `resolve_admin_uid` (same chokepoint as Remote Access); cloud Deploy/Tear-down show a confirm dialog because they create/delete billable resources (a manual row just generates a command — no confirm). The cloud deploy/tear-down responses stream NDJSON progress (like the Commit ⭐ button) into the card's live log.
- **JWT signing secret is generated, not hardcoded (changed 2026-06-28).** `app/auth/jwt.py` no longer falls back to the committed default `"webagent-dev-secret-change-in-prod"` (which let anyone forge an admin token and defeat every gate above). Order: `JWT_SECRET` env var → the git-ignored `data/config/jwt_secret.txt` → a freshly generated `secrets.token_urlsafe` persisted to that file (atomic O_EXCL create so first-run races converge). If the file can't be written it uses an in-memory random secret (logged loudly; tokens don't survive a restart). `app/admin/integrations.py` signs OAuth state tokens with the SAME secret via `jwt.get_secret()`. **Rotating the secret invalidates all live tokens → everyone re-logs in once** (expected on the first restart after this change, since the old in-memory default is replaced).
- **`resolve_admin_uid` requires a VERIFIED caller (changed 2026-06-28).** This is the shared admin gate for the `/admin/*` routers (deploy, storage, users, remote-access, tunnel-link, events, instances). It used to honour ANY client-supplied `requesting_user_id` that happened to be a DB admin — so an unauthenticated caller could send `requesting_user_id=admin` (the well-known bootstrap id) and get full admin. It now ignores the claimed id and grants access only to the **cryptographically-verified** caller from the request's JWT (Authorization header or `?token=`) when that verified user is a DB admin. The verified id is decoded once per request by the pure-ASGI **`CallerIdentityMiddleware`** (`app/auth/identity.py`, registered in `app/main.py`) and read from a contextvar — no route signatures changed. Frontend admin calls carry the token because the global `fetch` wrapper (`ui/shared/js/auth-refresh.js`) now proactively attaches the Bearer token to same-origin `/api/`+`/admin/` requests. **The `/admin/source/*` router** (`plugins/admin/source.py` — read/write/delete/**exec**) was previously reachable with NO auth at all (an unauthenticated remote shell); it now carries a router-level admin dependency and confines file paths to the project tree. The agent's own source tools call its in-process `_do_*` helpers directly, so locking the HTTP surface doesn't break them.
- **Files:** `app/deploy/` (store/credentials/base/bootstrap/registry/manager + `manual_common.py` shared clone-URL logic + `providers/google_vm.py`, `providers/ssh_vm.py`, `providers/termux.py`, `providers/windows.py`, `providers/macos.py` — each provider's `build_command()` is its command source of truth), the on-device scripts under `deploy/` (`termux-setup.sh` Termux-detecting; `start_server_linux.sh`; `windows-setup.ps1` + `start_server_windows.ps1`; `macos-setup.sh`) all committed, `app/api/deploy.py` (mounted in `app/main.py`; `/admin/deploy/command` builds the command + QR for any manual target, `/admin/deploy/termux/command` is a back-compat alias), UI in `ui/main-panel/app/settings/app-settings/` (`deploy.js` cloud row + the three manual rows via `MANUAL_ROWS`; the four Deploy rows in `app-settings.html`; shared `.ac-tx-*`/`.ac-deploy-cmd-*` CSS in `ui/shared/css/app3.css`).

## Social sign-in (drop-in providers) + access modes

**Access modes are now two, not three.** The app-level access policy
(`app/admin/settings.py`, `VALID_ACCESS_MODES`) is **Private** (`admin_approval`
— register, then wait for an admin to authorize) or **Open Registration**
(`public_registered` — anyone can join/sign in; anons get a guest token). The old
**open** auto-admin mode (no sign-in, local/tunnel auto-trust) was **retired**:
any saved `"open"` is normalized to `public_registered`, the `/open-login`
endpoint and the `open_mode_admin_id()` tunnel/local auto-admin shortcut are
**removed**, and identity now comes only from a valid JWT ("Remember me" covers
the local-convenience case). If you relied on tunnel-admin-without-a-token, sign
in normally and tick Remember me.

**Social sign-in** ("Continue with Google / GitHub / Microsoft / Apple") is a
drop-in provider tree — `plugins/auth_providers/<id>/<id>.json` (+ optional
`<id>.py` hook). The core lives in `app/auth_providers/` (discovery + a
vault-backed credential store) and `app/api/social_auth.py` (the endpoints,
mounted in `app/main.py`). Admins enable a provider and paste its keys in **Admin
Tools → Settings → Data Settings → App Access → Social sign-in**; keys go to the encrypted vault
(service `social_login:<id>`), never a plaintext file. It is **login-identity
only**, separate from the per-agent tool-connection OAuth in `app/api/oauth.py` +
`app/integrations/`.

- **Redirect URI:** every provider lands at
  `<base>/api/v1/auth/social/<id>/callback` (the admin card shows the exact
  string to register with the provider; base derives from `WEBHOOK_BASE_URL` /
  the request, same as the integration OAuth).
- **Secure context required at the provider side.** Google/Apple/etc. only allow
  `https` (or `localhost`) redirect URIs — a plain-`http` LAN address won't work;
  use a tunnel or a real domain (same rule the App Settings "secure-context
  features like Google sign-in need a tunnel" note calls out).
- **New accounts follow the access mode:** a first-time social sign-in
  auto-approves under Open Registration and awaits admin approval under Private.
  Accounts link by provider id first, else by email (so a Google login attaches
  to an existing same-email account rather than duplicating it).
- **Apple** is fiddlier (its `client_secret` is an ES256 JWT signed from a `.p8`
  key; its callback is a `form_post` POST; identity is in the `id_token`) — all
  handled in `plugins/auth_providers/apple/apple.py`.

## Runtime state files — gitignored

Any file the **running app writes to** is per-machine runtime data and, as a rule, must never be tracked by git. Tracking such files causes `error: Your local changes to the following files would be overwritten by merge` on `git pull` on the production VM, blocking deploys.

**Split SQLite authorities under `data/` are gitignored.** The v2 layout uses `data/db/app.db` for the control plane plus per-user and per-agent authority databases. Source code under `app/` must never contain runtime database files. Session inspection goes through authenticated APIs rather than direct SQLite access.

**Rule (every other runtime file):** before introducing a new file the backend writes during normal operation (auth blobs, caches, per-machine config, runtime backups, user-generated artifacts), add it to `.gitignore` in the same commit. If you discover one already tracked, untrack it: `git rm --cached <path>` + add to `.gitignore` + commit.

## First-boot security defaults (encryption on by default — safely)

A **fresh** deployment turns on the **OS-keyring secrets vault + per-tenant `field` encryption** automatically on first boot, so new installs protect stored credentials without anyone flipping a switch. This is a guarded one-time seed (`app/encryption/defaults.py`, called from `app.main:startup` next to the other first-boot seeds), **not** a change to the in-code fallback default (which stays `inline_db`/`none`).

It fires **only when every guard passes**, and is otherwise a clean no-op that leaves the install exactly as it was (re-seedable on a later boot):

- **not env-locked** (`WEBAGENT_CONFIG_SOURCE=env` installs configure the vault via env vars explicitly — the seed is skipped);
- **nothing decided yet** — neither `app/secrets_mode.json` nor `app/encryption_mode.json` exists (persisting them is the "already decided" marker, so an admin's later choice always wins and the seed never re-runs);
- **a real, secure OS keyring is present** (`keyring` resolves to a genuine backend — Windows Credential Manager / macOS Keychain / Secret Service — not the no-op `fail` backend or an insecure plaintext fallback) **and a live write/read/delete round-trip succeeds**;
- **the crypto dependency is present** (the `field` backend constructs);
- **the database has no stored secrets yet** (an empty `auth_elements`), so nothing existing is machine-bound or stranded.

Why guarded rather than always-on: `field` encryption keys live in **that machine's** OS keyring, not the DB. That's what makes it secure, but it means silently encrypting an *existing* install would bind credentials the admin never chose to encrypt — and a later DB restore on another box would strand them. The guards ensure encryption-by-default only ever lands where it's safe (fresh + keyring-capable), and headless servers with no keyring quietly stay on the plaintext default instead of failing to boot. **Operational caveat:** because the keys are machine-bound, a backup/restore or host migration must carry the OS-keyring entries too (master key at `wa:kek:active` under service `webagent_vault`), or back up the master key out-of-band — otherwise encrypted rows become unreadable on the new host.

## Full-database encryption at rest (SQLCipher) — opt-in, per-database

Separate from the per-tenant `field` encryption above (which encrypts only the credential `secret_ref` column): this encrypts each **entire SQLite database file** at rest — `local.db`, the attached `vault.db`, `logs.db`, `recordings.db`, `wiki.db` — chosen **per database** from Settings → Data Settings → Database → *Full-database encryption*. OFF by default.

How it works (`app/db/db_crypto.py` + `app/db/db_keys.py`):

- Each database file gets its own random 256-bit key. That key is **wrapped under the install KEK** (the same master key field encryption uses) and stored in the OS keyring at `wa:dbkey:<id>`. The vault is the single root of trust — the DB files hold no key material.
- Every SQLite connection site (`local._get_conn`, `logs_store._connect`, `wiki/db._connect`) routes through `db_crypto.connect()`, which picks the driver (SQLCipher when a file is/should-be encrypted, else stdlib `sqlite3`) and applies the key. **When nothing is enabled it is byte-for-byte the old `sqlite3.connect`** — zero behaviour change for installs that never turn it on.
- Toggling a database writes `app/db_encryption.json` (intent) and needs a **server restart**. At startup, `db_crypto.reconcile()` runs *before any store opens its files* and converts each file to match — plaintext→encrypted or back — **backup-first, atomic, with rollback and no plaintext residue** (the discarded plaintext is overwritten then deleted).
- Key application is driven by each file's **actual on-disk header**, not just config, so a config/file mismatch (e.g. enabled-but-not-yet-migrated) degrades safely instead of failing to open.

Requirements + guards: needs the optional **SQLCipher engine** (the `encryption` extra in `pyproject.toml` — `sqlcipher3` on Windows / `sqlcipher3-binary` on Linux) **and** the `os_keyring` secrets vault. If either is missing the admin UI refuses to enable it (501, clear reason) rather than faking success. `wiki.db` defaults OFF and is flagged in the UI because it is git-tracked and served as public pages.

> **The engine must be installed via the `encryption` extra, not by hand.** The Windows launchers run **`uv sync --extra encryption`** (`webAgent.bat`, `deploy/windows-setup.ps1`) — a plain `uv sync` would *prune* a hand-installed `sqlcipher3` (it's not a default dependency), and the next boot of an encrypted install dies with `sqlite3.DatabaseError: file is not a database` (the encrypted file opened with the plain stdlib driver). So once any database is encrypted, the engine is effectively **mandatory** for boot; keep the extra on every launch path that runs `uv sync`/`uv run` for the server.

**Operational caveat (bigger than field encryption):** the keys are machine-bound in the keyring. With whole-file encryption on, losing the keyring loses **everything** in those files, not just credential secrets — so backing up the KEK (`wa:kek:active` under service `webagent_vault`), or carrying the keyring on a host migration, is **mandatory**. A headless host with no keyring cannot enable this.

## Writing JSON config — route through the shared helper

The app is meant to ship with **no `data/` folder** — config files materialize lazily, only when a setting first changes. To make that safe, **every JSON config writer goes through `app/util/config_io.py`**, never a raw `open(...)` + `json.dump`:

- **`safe_write_json(path, data)`** — whole-blob write. Creates `data/config/` (and any missing parent) on demand, then writes atomically (temp file + `os.replace`). A save into an absent `data/` self-heals instead of raising `FileNotFoundError`, and a crash mid-write can never leave a truncated config.
- **`set_config_key(path, key, value)`** — change **only** that key (or nested path) and leave every sibling key intact, creating the file if absent. Use this for a single-setting save (e.g. one user's provider config) so concurrent saves of *other* keys aren't clobbered.
- **`read_json(path, default)`** — the matching read: returns `default` (never raises) on a missing or corrupt file.

Do **not** hand-roll `open(...) + json.dump` for a new config writer — you'll reintroduce the missing-folder crash and the truncate-on-crash risk this helper exists to remove. Cached config modules (e.g. `app/admin/ability_config.py`, `app/admin/page_config.py`) keep their in-process cache and merge logic, but their final disk write still goes through `safe_write_json`.

## Shipping with no `data/` folder — where read-only seeds live

`data/` is **purely runtime state**: nothing the app *needs* at boot lives there, so the app can ship with `data/` entirely absent and self-heal (every config reader falls back to a built-in default; the writers above create `data/config/` on first change; the SQLite DBs and `wiki.db` create themselves; `data/wiki.db` is the one deliberately-tracked seed and is optional at runtime).

The read-only **defaults the app genuinely needs** are therefore kept **out of `data/` and bundled under `app/defaults/`** (tracked, always present):

- `app/defaults/app-prompts.json` — the system/UI prompt catalog (served by `app/api/features.py`; read by `loop.py`, `suggestions.py`, `system_prompt_fragments.py`, `tasks.py`, `diag_investigate.py`, `communications/auth.py`).
- `app/defaults/agents/*.json` — the default + system agent-template seeds.

Both are resolved through **`app/util/paths.py`** (`app_prompts_path()`, `agents_seed_dir()`), which prefers a `data/` copy if one exists (a deployment override) and otherwise uses the bundled `app/defaults/` copy. **Rule:** a read-only file the app needs at boot belongs in `app/defaults/` (resolved via `paths.py`), never in `data/`; only files the app *writes at runtime* belong in `data/`.
