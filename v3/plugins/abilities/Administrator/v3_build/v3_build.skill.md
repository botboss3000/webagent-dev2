# V3 development release workflow

Use one stable task ID per source change. Call `v3_build_work(action="begin", mode="isolated", task_id=..., summary=...)` before editing. The receipt gives a private task workspace and its input digest. Other tasks may stay open or build while this task is edited. Use a seeded V3 source workspace for code work, review its complete text diff, then call `v3_source_apply` with that diff, the task ID, a stable request ID, and the task workspace digest from `v3_build_work.status`. The broker checks paths, digest and `git apply --check` before patching only this task's snapshot. Inspect `v3_source_receipt` after an uncertain apply; never create a second request ID to retry an uncertain write.

Run focused checks against the reviewed task source. After edits settle, read `v3_build_work.status` again and use that task's `workspace_inputs_sha256` in `finish`. Finishing freezes this task's source and immediately assigns its own durable job ID. The broker serializes candidate integration, locked Rust tests, Buildx image builds, and automatic V3 development deployment. An open second task does not delay this release. Concurrent changes to the same file fail with a source conflict; register a new task from the current release to revise them. A task ID is single use.

The release containers mount versioned code, config, abilities and UI assets from the frozen candidate. A source edit in another task workspace or the writable File Manager checkout cannot change those mounted release assets. Direct checkout edits are outside this release queue and are not a substitute for `v3_source_apply`. Only the broker chooses the development container targets; production is never a target. The previous containers and private image archive remain for rollback. An uncertain external effect requires reconciliation before another release.

After both replacements are healthy, the broker promotes changed release files
into the shared checkout if those paths still match the prior or new release.
A conflicting direct checkout edit holds subsequent releases for reconciliation.

Poll `v3_worker_job` about every 15 seconds while active, for no more than 30 minutes. Report only a terminal job status, phase, bounded sanitized reason or log excerpt, and job ID. On success, confirm both V3 containers running and healthy with `v3_build_status`. On timeout or disconnect report **still pending** and resume from the same task or job ID; do not resubmit a build. An idle agent cannot be awakened by polling alone. Approval and live automatic-deployment policy are required when finishing; revocation stops queued or running work. Abandon only an open task whose edits are no longer intended for release.

Codex uses the same broker through server-side `buildctl.py`: `begin` defaults to an isolated workspace, `inputs --task ID` reads its digest, `finish ID --expected DIGEST` queues one release, and `wait ID` polls without creating a job. The V2 Python bridge uses the same task registry and its own authenticated caller identity. Legacy shared-checkout work must not overlap isolated tasks.
