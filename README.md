# WebAgent

A **FastAPI** service with a **tool-calling** LLM agent (OpenRouter), optional **Supabase** or **local SQLite** persistence, and a **vanilla JS** UI at **`/index.html`** (static assets under `/ui/`).

> **📖 Full feature docs live in the in-app Wiki** (`data/wiki.db`). The list below is a
> brief index - each line links to its Wiki article. Open a link with the app running

> user-facing behaviour, update the Wiki article rather than this README - see
> `docs/claude/repo-conventions.md`. Developer/architecture, setup and deployment detail
> stays below.

### HTTP + WebSocket Architecture

The agent loop (`app/agent/loop.py`) runs as a **supervised background task owned by the Run Manager** (`app/agent/run_manager.py`), independent of any client connection. All user messages enter via **HTTP POST** (no WebSocket sends): `POST /api/v1/chat/send` saves the message + starts the run and returns immediately. The WebSocket is a **receive-only subscriber** — connected once per user, it receives events for all of that user's sessions. The DB is the source of truth (assistant answers stream into `interactions`; `session_runs` tracks the live turn); the WebSocket is a live accelerant.

```text
       [CLIENT]
          |
          |--- (HTTP POST) ---> [ app/api/chat.py ]   send message; run starts server-side
          |                           |
          |                    +-- POST /api/v1/chat/send    (fire-and-forget; primary)
          |                    +-- POST /api/v1/chat/stream  (SSE fallback; tails the run)
          |                    +-- POST /api/v1/chat         (buffered, inline)
          |                    +-- POST /api/v1/chat/interrupt  (graceful stop)
          |                    +-- POST /api/v1/chat/prewarm (build read-only prep while typing)
          |                           |
          |                    [ app/api/uploads.py ]        POST /api/v1/upload
          |                    store_file()  → bytes saved + attachment row
          |                           |
          |                           v
          |              +--------------------------+
          |              | SUPERVISED BACKGROUND RUN|
          |              | run_manager -> loop.py   |
          |              | (survives disconnects)   |
          |              +--------------------------+
          |                           |
          |              events emitted to:
          |              ├── SSE response body     (primary chat bubble display)
          |              └── Listener registries:
          |                    ├── _visualizer_listeners[session_id]   (per-session WS)
          |                    └── _user_listeners[user_id]            (per-user WS)
          |                           |
          |                           v
          |--- (WS receive-only) -> [ app/api/agent.py ]   /api/v1/agent/ws
                                      mode: "user_subscriber"
                                      optional resume: { session_id: last_session_seq }
                                      receives: stream, response, tool_call,
                                                tool_result, pipeline, db events
                                      for ALL sessions belonging to user
                                      On (re)connect, replays any buffered
                                      events with session_seq > last seen
                                      from app/agent/run_buffer.py.

Events are routed on the frontend:
  - "stream" / "response" events for the CURRENT session → chat bubble
       (SSE drives the bubble for the in-flight POST; WS takes over for
        replays after refresh / session-switch via
        `appendStreamToActiveBubble` and `finalizeAgentResponse`)
  - "tool_call" / "tool_result" / "pipeline" / "db" events → stream/loop/flow debug panels
  - Every event carries `session_seq`; the client tracks the highest seq
    per session in `app.lastSessionSeq` so the next WS handshake can
    request replay of only-newer events.
```

### Backend (`app/`)

| Module | Role |

Cross-platform — the channel is a socket, no PTY/winpty. A failed connect closes the tab with the reason via a `{"type":"error"}` frame + WS code 4002. The section self-hides when no servers are saved; rows with no stored login are shown disabled) + **`GET /api/v1/terminal/claude-resume-target`** + **`GET /api/v1/terminal/tmux-sessions`** + **`POST /api/v1/terminal/tmux/send-keys`** (deliver one named key — currently **Shift+Tab** → tmux `BTab` — to a tmux session's active pane via `tmux send-keys`; body `{"session","key"}`, admin-only, session name validated. The browser keybar routes **Shift+Tab** here for **tmux tabs** because a TUI running inside tmux 3.x — e.g. **Claude Code** — negotiates extended keys with tmux and then ignores the legacy back-tab `\x1b[Z` the keybar would otherwise inject raw; letting **tmux** originate the key means it's encoded to match the pane's current keyboard mode. Non-tmux tabs and all other keys keep the raw-byte path. Front-end: `_parseTmuxSession` records a tab's tmux session name from its launch command and `_sendTmuxKey` in `ui/shared/js/files.js` calls this endpoint, falling back to the raw `\x1b[Z` on any failure) + **`POST /api/v1/terminal/paste-image`** (multipart `file=` — saves a pasted/dropped image under `data/uploads/terminal-paste/` and returns its **absolute server path**, which the frontend then types (double-quoted) into the terminal so **Claude Code** ingests it via its "image file path in the message" route; needed because the web terminal is a **text-only pipe** an image can't pass through, and Claude's own Ctrl+V reads the *server's* OS clipboard not the browser's — useless over the tunnel. Admin-only; prunes saved files older than `TERMINAL_PASTE_RETENTION_HOURS`, default 24h. Front-end: the keybar **Paste** chip reads an image off the clipboard via `navigator.clipboard.read()` and an image dropped onto the terminal is handled the same way — both in `ui/shared/js/files.js` `uploadTerminalPasteImage`). **Quick-launches** are sidebar shortcuts that open a new terminal tab. A short **tap** types the plain `command` (a one-off process in a normal terminal window); an optional `tmux_command` is run instead on a **long-press** (≥500ms) — the same thing wrapped in a named tmux session so it survives tab close/refresh and is reattachable from any device (a small "in tmux" confirmation flashes). Rows with no distinct `tmux_command` (e.g. `tmux attach`/`tmux ls`/plain shell) behave the same either way. One entry instead carries `action:"claude-resume"` — the **"Resume Claude"** launcher, resolved server-side at click time by `claude-resume-target` (which returns both a plain `command` and a `tmux_command`, tap vs long-press), which scans `~/.claude/projects/*/*.jsonl` (newest first), drops any conversation **already open** — two unioned signals: (1) a live **web-terminal tab** is running it (each "Resume Claude" tab connects with `?claude_session=<id>`, stashed on its `TerminalSession`; **cross-platform**, so a second click correctly skips to the next-newest on Windows too, and self-clears when the tab is closed), and (2) on Linux/Termux only, a `/proc` open-fd + `--resume <id>` command-line scan (also catches `claude` started by hand outside WebAgent) — reads the winner's `cwd` **and name** (its `ai-title`, falling back to a summary / first user message) out of its transcript, and returns a **two-line** `cd '<cwd>'` + `claude --resume <id>` command (newline-separated, **not** `&&` — typed line-by-line with a real `\r` after the prompt settles, so it submits correctly in Windows PowerShell as well as bash) plus that conversation name as the tab label (or a fresh `claude` when nothing's resumable). Multi-session browser shell (PTY / **`pywinpty`** on Windows). One `TerminalSession` per client-supplied `session_id`, kept alive across WS reconnects so refresh / browser-close doesn't kill a running shell. A **tombstone channel** (`tombstones.py`, `hybrid_tombstones`) carries HARD deletes the watermark pull structurally can't: a permanently-deleted `sessions`/`agents` row vanishes from the remote so peers can never pull the erasure — the deleting device records a tombstone and every peer's `pull_tombstones` applies the matching local delete (cascading to the transcript), so a permanent delete converges everywhere within a tick instead of leaving a ghost until cold start. (Soft deletes instead ride the normal watermark pull, now that recycle/trash bump `updated_at`.) Money + coordination never pass through here. **Started in the app lifespan** (`app/main.py`) when the hybrid is on, **push + pull** (`pull_enabled=True`, Stage 4) after the security audit confirmed no authorization/identity/billing read resolves from the local cache; per-process, not via the cluster leader. **Idle round-trip suppression:** each pull is a remote round-trip even when nothing changed, and a permanently-empty table (no local watermark) used to do an unfiltered full scan every tick forever — so the puller now applies an **adaptive per-table backoff**: a table that returns nothing for `WEBAGENT_SYNC_QUIET_AFTER` (default 3) consecutive ticks is only re-checked every `WEBAGENT_SYNC_QUIET_SECONDS` (default 15s) while the engine is idle, cutting the steady-state background tax from ~10 round-trips/tick to ~1-2. The backoff is driven by "did this pull return rows", so any table with real cross-device activity resets to eager on its own, and it's bypassed entirely while a live turn is pushing (tombstones are always pulled every tick so deletes stay prompt). A `WEBAGENT_SYNC_STARTUP_DELAY` (default 5s) holds the first full sweep so it doesn't fight the first page-load API burst after a (re)start. Covered by `temp/test_hybrid.py` (incl. the audit-as-code guard) + `temp/verify_stage2_live.py` / `verify_stage4_live.py`. |

**Boot sequence.** A pre-paint inline script in `index.html` applies the saved theme + panel visibility before first paint, then a full-screen **boot curtain** (`#boot-curtain`) covers the whole app while it assembles — so the user never sees the bare shell, partials injecting, the theme settle, or the splash fade in; the curtain lifts only when the page is already in its intended view. It is the first child of `<body>` (critical CSS in `<head>`), so it paints on the first frame as an opaque, theme-coloured (`var(--bg-0)` — deep near-black in dark mode) overlay with a centered branded loading animation, at a z-index above the splash. A small header spinner (`body.is-booting`, removed by `ui/shared/js/tabs.js` once the saved tab mounts) still runs behind it. The curtain is lifted by `window.__boot` (defined inline near the top of `<body>`): `appReady()` fades it once the app shell + saved tab are mounted **when no splash is showing**; if the splash plugin claims it (`splashWillShow()`), the curtain instead stays opaque until the splash has fully faded in and then hands off (`splashReady()` → black → splash, no shell flash). `reveal()` is forced on the server-down path and by a 10s safety net so boot is never trapped on the curtain.

**Boot fetch coalescer + deferred non-critical calls (cold-load perf).** The boot fires ~30 API GETs from ~15 independent modules with **no shared fetch helper** (`config.js` only builds URLs), and several hit the SAME endpoint near-simultaneously (measured: `/user/profile`, `/agents`, `/auth/ui-config` each ×3, plus six more ×2). Over HTTP/1.1 the browser opens only ~6 sockets/origin, so each redundant GET burns a scarce socket and starves the session/message/roster loads that gate first paint. Two mitigations: (1) a classic inline `<script>` near the top of `<body>` (before the first boot fetch and before any ES module) wraps `window.fetch` to **coalesce duplicate same-origin `/api/` GETs** — concurrent identical requests share one round-trip (each caller gets its own `Response.clone()`; the master is never consumed), and a 2s replay cache (boot window only, OK responses) collapses near-sequential repeats. Only bodyless, signal-less GETs are touched; everything else (POST, cross-origin, signalled, `Request`-object form) passes straight through, wrapped in a try/catch that falls back to native fetch. Guard: `window.__bootFetchCoalesced`. This cuts the boot from ~32 to ~18 requests. (2) Decorative inits — `initBilling` (credit pill + its one balance GET; real polling still starts later via `startBilling`) and `initRecorder` (config probe) — are moved OUT of the eager `_safeInit` burst and run only **after the curtain lifts**: `reveal()` sets `window.__boot.revealed` and dispatches a `webagent-app-ready` event that `main.js` listens for (idle-callback, with a `revealed`-flag guard for the attach-too-late race), so they queue behind the critical calls instead of competing with them. **Bump `sw.js` `CACHE` on any change to boot JS** — module JS is precached; `index.html` itself is network-first so inline changes load without a bump, but `main.js` needs one.

**Combined boot endpoint (`GET /api/v1/boot`).** The single biggest cold-load lever: instead of the browser firing the ~12 stable-key boot GETs one-by-one (queued behind the 6-socket HTTP/1.1 cap), the coalescer fires ONE early `GET /api/v1/boot` (before any ES module) that returns them all in a single round-trip, and **primes the coalescer's cache** from it — so each module's later fetch is answered from memory with no socket. The server aggregator (`app/api/boot.py`, a thin **read-only accelerator**, not a plugin capability) gathers each section by calling the SAME handler the individual endpoint uses, from within the `/boot` request's own context — so caller identity (the `CallerIdentityMiddleware` contextvar) and every per-endpoint authz check run identically, with zero duplicated auth logic. Sections folded in: `access-mode`, `ui-config`, `app-prompts`, `app-prompts/ui-messages`, `chat/suggestions/config`, `abilities/catalog`, `pages/catalog` (public) + `files/check-access`, `user/profile`, `agents`, `db/sessions` (list, `limit=50`), the **first transcript page** of the session being opened (`db/session-messages`, newest 40, light — the ~7s tail), and the **chained `agents/{id}/abilities` tail** (user-scoped). The client sends `?session_id=` so the server can (a) return that session's newest-40 light transcript — matching `session-load.js`'s common-case open (`_OPEN_NEWEST_LIMIT`; a scrolled-up session opens with an `around_id` key instead and is deliberately NOT primed) — and (b) resolve the agent bound to that session (read off the sessions list it already loaded) for the abilities tail, rather than guessing. A wrong guess (or an `around_id` open) only means a re-fetch, never wrong data. Every section is OPTIONAL: on any error it is omitted and the client falls back to its own fetch (a cache miss), so `/boot` can never break boot. Client mechanics (in the `index.html` coalescer): a `normKey()` that drops the caller-identity params `?token=` and `?user_id=` (constant during one boot, and modules disagree on whether to send `user_id`) and sorts the rest, so every caller of an endpoint shares one key; a `primed` map (served for the whole boot window) plus an `expected` set so a module GET that races ahead of `/boot` waits for it instead of opening a redundant socket. The boot window is **20s** (`BOOT_WINDOW_MS`) so the DEFERRED tutorial/hints reconcile of `ui-config`+`profile` (fired after the curtain lifts, well past 12s on a slow remote DB) still hits the primed snapshot. **Known boundaries (by design):** `appearance.js` fetches `ui-config` render-blocking in `<head>` BEFORE the coalescer installs (pre-paint theming), so that one call stays on the network — it runs parallel to `/boot`, not on the tail; the transcript is aggregated only for the common newest-40 open (a scrolled-up `around_id` open re-fetches); and `/db/sessions/{id}/related` (per-session, lazy, variable key) is not aggregated and keeps flowing through the normal coalescer + network. Measured (remote-Supabase, signed-in chat boot): the whole boot burst — the four previous worst offenders (`abilities/catalog`, `agents`, `app-prompts`, `user/profile`, each ~12s under socket starvation), the chained abilities tail, and the session transcript (~7s) — collapses into one ~2.3–3.3s `/boot` call, verified serving each section from memory with zero network hits.

**Agents-page detail (`GET /api/v1/agents/{id}/connections`).** Opening an expanded agent card fires this (ability/member badge counts). It was ~13s on a remote DB because it made ~20 serial per-service `auth_element_get` round-trips — mostly inside `get_admin_configured_providers` (`app/admin/integrations.py`), which looped `auth_element_get(<admin>, service, …)` per channel + per connection provider. Both that helper and the handler now pull the relevant `auth_element`s in ONE `auth_element_list` query and index by service, cutting it to ~3s (`get_admin_configured_providers` alone: ~5.8s → ~0.9s). The handler's independent per-agent reads are also issued together via `asyncio.gather` (though the current hybrid-remote DB layer still services them serially, so the batched auth lookup is the actual win).

Two settings under **App Config → App Settings**, persisted per browser in `localStorage`:
- `bootAnimation` (values: `chat-slide-right` (default), `chat-slide-left`, `no-animation`) — picks the reveal transition.
- `pagesCatalogCache` (localStorage, written by `header-build.js`) — a cached copy of the page catalog used **only** to pre-paint the header tab strip synchronously before first paint (no flash for returning users). It is NOT the source of truth — the order/names/icons/visibility of pages are an **admin preference stored server-side** (see **Pluggable pages** below). The cache is refreshed from `GET /api/v1/pages/catalog` on every load.

| `WEBAGENT_SECRET_*` | When the secrets provider is `env`, secret keys map to env vars with this prefix (e.g. key `db_password_postgres` → `WEBAGENT_SECRET_DB_PASSWORD_POSTGRES`). |
| `VAULT_ADDR` / `VAULT_TOKEN` | HashiCorp Vault server URL + token — required by the `hashicorp_vault` secrets provider (needs `hvac`). Optional `VAULT_KV_MOUNT` (default `secret`) and `VAULT_KV_PREFIX` (default `webagent`) select the KV v2 mount + path prefix. |
| `AZURE_KEY_VAULT_URL` | Azure Key Vault URI (e.g. `https://my-vault.vault.azure.net`) — required by the `azure_key_vault` secrets provider (needs `azure-keyvault-secrets` + `azure-identity`; auth via `DefaultAzureCredential` — service-principal env vars or Managed Identity). |
| `GCP_PROJECT` / `GOOGLE_CLOUD_PROJECT` | GCP project ID — required by the `gcp_secret_manager` secrets provider. |
| `AWS_REGION` | AWS region — used by the `aws_secrets_manager` secrets provider. |

In **local** mode, Supabase vars are not required for storage; you still need **`OPENROUTER_API_KEY`** (and usually **`OPENROUTER_MODEL`**) for LLM calls.

Provider, API key, and model can **also** be configured at runtime via the ⚙️ **Settings** modal in the UI (gear icon next to Cloud/Local toggle). Changes are saved to **`data/config/provider.json`** and applied on next server start. The API key is masked in the UI after saving.

**One default model, user-switchable per chat (no racing):** each agent runs **exactly one** model per turn — the **default**. Parallel model racing was removed. The default is chosen explicitly with a **"Default" radio** in the model table (left of the Text/In/Out columns); it's stored as the top-level `model` of the provider config (admin) or the agent's `metadata['llm_config']`. The saved-model **roster** (`multi_providers`) is still kept, but it is *not* raced — it only supplies the candidate list for the chat model-switcher and the vision / image-out worker picks.

**Per-agent model lists:** an individual agent can carry its **own** roster — stored in `metadata['llm_config']` as `{use_default, provider, base_url, api_key, model, multi_providers:[…]}`, where `model` is the chosen default. At run time `_agent_llm_override` / `_merge_agent_override` (in `app/admin/settings.py`) merge it over the app default (resolution order **app-default → agent → session**). The model-table UI for both the **admin default** (App Config → Agent Settings → Models) and the **per-agent** config (agent card → Config → LLM) is one shared, instantiable component, **`ui/shared/js/model-table.js`** (`mountModelTable`); the two mounts are sister panels (`SISTER-PANEL: MODEL-TABLE`). When the admin's **"Extend default LLM to agents"** is on the per-agent table shows the app-default models as read-only **"Inherited"** rows plus the agent's own editable rows; when off, only the agent's own models are shown. **Load path (perf):** the table shows its frame immediately (kept collapsed) and fetches the provider preset list (instant local fallback) in parallel with the saved config, rather than hiding the whole panel behind one spinner until the DB read returns. There is no separate "loading" strip — the only load indicator is a spinner shown **on the + (add-a-model) button** while the provider's available-model list loads (that fetch, `loadModels` → `GET /admin/settings/models`, is the one genuinely slow call; it powers the "Search models…" box, so its spinner sits on the control that opens the add form). The saved config itself is read in ONE call — **`GET /admin/settings/provider-bundle`** returns the default-model provider config **and** the saved-model roster from a single server-side vault+DB resolve, replacing the two sequential `GET /provider` + `GET /multi-providers` round-trips (which each repeated the same per-user vault decryption); the front-end falls back to those two reads in parallel if the bundle endpoint is unavailable.

**Model metadata catalog:** `app/model_catalog.py` is a self-contained library that merges two public, keyless sources — **models.dev** (`https://models.dev/api.json`, the backbone: context window, max output, input/output/cache cost, capability flags, modalities, family, release date across OpenAI / Anthropic / Google / Mistral / xAI / Meta and more) and **OpenRouter** (`https://openrouter.ai/api/v1/models`, written descriptions + extra coverage). The merged map is keyed by model id (matched on both full ids like `openai/gpt-5` and bare ids like `gpt-5`, with the picker's selected provider preferred for bare-id resolution) and cached to **`data/config/model_catalog.json`** with a fetch timestamp — served from cache instantly and re-fetched only when stale (> 24h) or forced. With this in place, `GET /admin/settings/models` enriches each model with `context`, `max_output`, `cost_input`, `cost_output`, and `description`, which the Settings model picker shows as context/cost badges per row and a metadata panel (chips + description) for the selected model. Endpoints: `GET /admin/settings/model-catalog` (cache status), `POST /admin/settings/model-catalog/refresh` (force re-fetch), `GET /admin/settings/model-info?model=<id>` (full merged metadata for one model), `GET /admin/settings/current-model-info?agent_id=<id>&session_id=<id>` (resolves the requesting user's *active* model exactly as a run does — app default then any per-agent override then any per-session override — and returns its context/max-output/cost in one call). The chat footer uses that last endpoint to show the active model's context window and max output (e.g. `ctx 1M · max 384K`) next to the in/out token counters; it refreshes when the model is changed in Settings (via `app.refreshModelContext`). **A dedicated "model" button below the chat pill** (`#chat-model-btn`, in `.chat-footer-right` next to the Ask/Plan/Auto pill) shows the active model's short name and opens an in-place model picker (`ui/shared/js/chat-activity.js`); the footer context chip is also still clickable. The picker is a floating panel anchored to the **left edge of the chat pill**, sitting **just above** the context-details line, themed with design-system variables (correct in dark + light). Its list is **curated, not the full provider catalog** — it shows **all of the agent's Text-capable models** (the union of the app default(s) + the agent's own roster, resolved server-side by `GET /admin/settings/agent-models?agent_id=<id>&session_id=<id>` exactly as the run resolves it). It falls back to the admin defaults (`GET /admin/settings/multi-providers`) when there's no agent/session. Each row shows the model's context size, the **total tokens that model has used in the current session**, and (in a detail footer for the focused row) its description + input/output cost per 1M tokens. **Picking a model is per-session by default:** in a chat it saves the choice on the **session** (`POST /api/v1/chat/session-model` → `sessions.metadata.llm_config`), so each conversation remembers its own model without touching the agent default or other sessions; with an agent but no session it overrides the agent's `llm_config.model`, and with neither it updates the global provider model. The switch takes effect on the **next turn** — the loop re-resolves the effective model every run as **app-default → agent → session** (`apply_provider_for_run` in `app/admin/settings.py`). Confirmation is an inline **spinner → green-check** (red cross on failure). The per-session per-model totals come from **`GET /admin/settings/session-model-usage?session_id=<id>`**, which sums input+output tokens **and `cost_usd`** per `model` for the session, scoped to the requesting user. The library lives outside `app/admin/` so model metadata keeps working if the admin package is removed.

**Accurate cost accounting (per call, per model).** Every LLM call records a row in **`usage_events`** carrying its `model`, `provider`, tokens, **and a locked-in `cost_usd`** — computed at save time from that model's published per-1M price (`app/model_catalog.cost_for`) × the call's tokens, so the figure never re-prices when a session later switches models. The table also gained a direct **`session_id`** and a **`source`** tag (`chat` vs `background:*`). **Background (non-chat) LLM calls are metered too** — git commit-message generation, the chat-pill suggestion text, the App-Settings page-assistant placeholder ideas (label `page-suggest`; **`POST /api/v1/app-prompts/page-suggestions`** → `app/agent/suggestions.py` `generate_page_suggestions`, which turns the hovered section's `suggest` hint in `app-prompts.json` into rotating example requests shown in the pill's placeholder — grounded in the app's CURRENT pages (`app.ui_pages.ui_catalog`, so it proposes new pages and never duplicates existing ones) and the default WebAgent's MEMORY of the user (`db.memory_search` fast FTS path) so some ideas are personalised), context compaction, and embeddings each write a `source='background:*'` row via **`plugins/billing/usage.py` `record_background_usage`** (attributed to a `system` owner), so app-wide totals include them. Summing `cost_usd` then powers three surfaces: the chat footer's **session cost chip** (a running per-call sum — `_sessionCostUsd` in `chat-activity.js`, reconciled on load against **`GET /admin/settings/session-cost?session_id=<id>`**, so it stays correct across mid-session model switches); the **agent config tab's "Usage & Cost"** block (total + per-model breakdown from **`GET /admin/settings/agent-usage?agent_id=<id>`**, scoped to the **(viewing user, agent)** pair — what *this* user has spent with *this* agent, not the agent's all-users total; every row of that model table, inherited app-default models included, reports the same per-(user, agent) figure, and the table's "Reset Usage Counters" clears only the viewer's own rows); and the **admin Agent Settings model table**, whose usage cells call **`GET /admin/settings/model-usage?model=<id>&provider=<p>&scope=global`** — `scope=global` (admin-only) sums every agent, user, and background task app-wide and returns `total_cost_usd` (the canonical published-price figure) alongside the provider-billed `total_cost_cents`.

**Per-model reasoning effort (manual + agent-driven):** alongside *which* model runs a chat, each chat can set *how hard* the model thinks — the provider's reasoning-effort dial (`minimal → low → medium → high`, plus **default** = send no hint). In the footer model picker every reasoning-capable model row carries a small effort selector (Default · Min · Low · Med · High); the choice is **remembered per model** for the session. It saves via `POST /api/v1/chat/session-model-effort` into the same `sessions.metadata.llm_config` as the picked model, under a `model_effort` map (`{model id → level}`) — kept separate from the picked model so switching models preserves each model's level, and surviving a model swap. The level is resolved per run by `_resolve_session_effort` (in `app/admin/settings.py`) for whichever model is active and stashed in `LLM_REASONING_EFFORT`; the agent loop sends it as `extra_body.reasoning.effort` on the LLM call and, if the provider rejects the param or level, drops it and retries once (so an unsupported effort never breaks the turn). `GET /admin/settings/current-model-info` also returns the active `reasoning_effort` and the model's `reasoning` capability flag. **The Model Switcher ability** (`plugins/abilities/Core/model_switcher/`) lets the agent drive both dials itself: it rates a task's difficulty and either keeps the default model but calls `set_effort('<level>')`, or switches model *and* sets its effort, then calls `reset_to_default()` (clears both the picked model and all per-model effort) when the task is done. Raising effort or upgrading the model is confirm-gated (asks before spending more); lowering or reverting is free. Its **Model switching** posture knob (Conservative / Balanced / Eager) biases how proactively it right-sizes both.

**Context-compaction control layers.** Context Control exposes **Compaction Target Tokens** (`compact_target_tokens`, default 100K) and **Keep Verbatim Tokens** (`verbatim_tail_tokens`, default 30K) as absolute per-agent ranges under Knowledge. The chat footer may override those token amounts for one session through `/api/v1/chat/session-compaction`. App Functions owns the 1.05M-token hard ceiling plus advanced car/model defaults. Effective order is app defaults/ceiling → agent token budgets → optional session override; the active model window is always capped by the app maximum. Legacy fraction overrides are read and converted during migration, but new saves use tokens only.

## Installation

> Plain-English versions in the Wiki: [Installing & Running WebAgent](http://localhost:8080/?tab=wiki&article=installing-running-webagent) and [Supported Devices & Platforms](http://localhost:8080/?tab=wiki&article=supported-devices-platforms). The exact commands and flags are below.

**Supported Python:** 3.11 through 3.14 (pinned via `pyproject.toml` `requires-python = ">=3.11,<3.15"`). The launchers and deployment images prefer Python 3.14 while retaining compatibility with 3.11–3.13.

1. Clone the repository and enter the directory.

2. **Windows quick path:** double-click **`WebAgent.bat`**. It will:
   - Install **uv** (Astral's Python + venv manager) if missing — via the official PowerShell installer.
   - Run `uv sync --python 3.14`, which downloads Python 3.14 into uv's cache if needed, creates `.venv` in the project root, and installs all deps from `pyproject.toml` / `uv.lock`.
   - If the existing `.venv` was built with an unsupported Python, the script removes it so uv can rebuild cleanly.
   - Start the server with auto-restart on exit.

   On subsequent boots, `uv sync` is idempotent and near-instant when deps haven't changed.

   **Manual / non-Windows (uv path, recommended):**

```bash
# Install uv if not already present
curl -LsSf https://astral.sh/uv/install.sh | sh

# Sync deps + Python (idempotent)
uv sync --python 3.14

# Run the server
uv run python run.py
```

   **Manual / non-Windows (legacy pip path):** still works — `requirements.txt` is maintained alongside `pyproject.toml`.

```bash
python -m venv .venv
source .venv/bin/activate    # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

3. **Cloud (Supabase)** — If you use **`cloud`** mode, apply your team’s canonical schema (often the **Web Portal** monorepo migration, e.g. `Web Portal/supabase/migrations/20260130120000_webagent_complete_schema.sql`, when that sibling repo exists). The **`migrations/`** folder in *this* repo holds extra or historical SQL; read **`migrations/README.md`** for how it is being used.

  > **New (v0.3+):** `007_create_channel_identities.sql` and `008_create_linking_codes.sql` add tables for the communication plugin system (Telegram, WhatsApp, SMS). The **local** backend auto-creates these; on **Supabase**, apply via the SQL editor.

  > **New (v0.4+):** `009_multi_agent_system.sql` adds the `user_profiles` table (admin flag, default agent), extends `agent_templates` with `name`, `description`, `icon`, `trigger_description`, `can_be_default`, `is_system`, `is_pipeline`, `access_level` columns, extends `agents` with `template_id`, `owner_user_id`, `is_user_default`, `is_pipeline` columns, and seeds the default/optimizer/admin-agent templates. The **local** SQLite backend auto-applies these columns; on **Supabase**, run via SQL editor.

  > **New (v0.5+):** The **local** SQLite backend auto-applies two new columns to the `agents` table: `allowed_tools` (JSON array of disabled Tier-2 tool names — empty = all enabled) and `custom_tool_ids` (JSON array of opted-in DB tool IDs). These drive the interactive Agent Loop diagram editor in the UI. The `agents.py` API exposes `model`, `temperature`, and `max_tokens` as user-editable fields via `PUT /api/v1/agents/{id}`. Tool filtering is enforced at runtime in `app/tools/loader.py` so the LLM never sees disabled tools in its schema.

  > **New (v0.6+):** **Loop Logic Engine** — the `loop_logic` column (already present as `TEXT NOT NULL DEFAULT '[]'`) now drives runtime gating of five optional agent loop steps: `interrupt_chk`, `permission_chk`, `guardrails`, `delegation_chk`, and `skill_track`. Store a JSON object array (e.g. `[{"node": "skill_track", "enabled": false}]`) to selectively disable steps; a flat string array or empty array means all steps run (backward-compatible with existing agents). `LoopConfig` in `app/agent/loop_executor.py` parses this column and is called by `loop.py` before each gated step. The Agent Loop diagram in the UI lets users toggle these nodes per-agent; disabled nodes appear muted with a strikethrough label. No schema migration is required — the column already exists.

  > **New (v0.7+):** **Configurable Guardrails** — two new columns drive per-agent safety policies. `agents.safety_policy` (JSON) stores `destructive_tools` (tool names added on top of the hardcoded baseline), `auto_confirm` (skip the confirmation gate for automation agents), `blocked_imports` (extra modules forbidden in `create_tool`), and `max_concurrent_tools` (cap parallel tool execution). `tools.requires_confirmation` (boolean) marks individual user-created tools as destructive. At runtime `loop.py` merges all three sources into a single effective set — the hardcoded baseline (`DESTRUCTIVE_TOOLS`) ∪ `safety_policy.destructive_tools` ∪ any loaded tool with `requires_confirmation=True`. A **Safety & Guardrails** section in the agent Config tab lets users manage these settings with no code changes. The local SQLite backend auto-applies the schema via ALTER TABLE migrations; on **Supabase**, run `migrations/012_safety_policy.sql` via the SQL editor.

  > **New (v0.8+):** **Row ordering** — `agents.sort_order` and `sessions.sort_order` (both nullable `INTEGER`) persist the user's manual **drag-to-reorder** order for the Agents page and the chat-header session dropdown (each row has a grip handle). The agent order is applied on the Agents page (🤖); the session order applies in the chat-header session dropdown (which now spans all agents). Order is written by index via `POST /api/v1/agents/reorder` and `POST /api/v1/db/sessions/reorder` (account-level, so it follows the user across devices), and read back via the `(sort_order IS NULL), sort_order ASC, …` clauses in `list_agents_for_user` and the sessions list query (pinned rows still float to the top). The shared frontend helper (pin state, display sort, and the pointer-based drag that works on mouse + touch) lives in `ui/shared/js/ordering.js`, imported by both `ui/chat/js/session-core.js` (the dropdowns) and `ui/main-panel/agents/js/agents.js` (the Agents page). The local SQLite backend auto-applies the columns via ALTER TABLE migrations; on **Supabase**, run `migrations/024_row_ordering.sql` via the SQL editor.

4. Run the server:

```bash
uvicorn app.main:app --reload --host 0.0.0.0 --port 8080
```

**Windows users:** `WebAgent.bat` (described above) is the recommended path — it handles venv creation, dependency install/update, and auto-restart. Internally it invokes `run.py`, which **guarantees a single server instance**: before binding it kills any process already listening on port 8080 (take-over policy — a killed mid-turn run is recovered by the app's startup orphan-cleanup) and then binds the port **exclusively** (no `SO_REUSEADDR`). This matters because the live chat WebSocket and the running agent only share events through one process's memory; if two servers stacked on :8080 (which Windows `SO_REUSEADDR` used to allow), the OS split connections between them and live messages silently failed to stream while still landing in the shared DB.

**TUI launcher (optional, prettier than .bat):** the `launcher/` directory builds a portable `webagent.exe` (Textual-based TUI, Lucide bot icon) with buttons for Launch / Restart / Stop / Open Browser / Clear DB / Reset Python / Full Reset, plus an animated procedural ASCII background with cycleable color presets (phosphor, amber, cyan, vaporwave, neon tide, rainbow, fire, ice, …). Config (project path, theme) persists at `%APPDATA%\WebAgent\launcher.json` so the .exe can sit anywhere. To build: `cd launcher && uv sync --extra build && uv run python scripts/build_exe.py` → `launcher/webagent.exe` (single file, no scratch folders left behind). To run from source: `cd launcher && uv sync && uv run python -m webagent_launcher`. Keyboard shortcuts and feature list in `launcher/README.md`.

**Unix:** `bash scripts/start_WebAgent.sh` (background + logs).

**Android (Termux + proot-distro Ubuntu):** the `launcher_android/` directory is the Android counterpart to `launcher/` — a Textual TUI with Launch / Restart / Kill / Browser buttons plus a dependency **Doctor** that surfaces venv / `.env` / apt build-deps / per-package pip status and offers one-tap fixes. The known Android-ARM blocker (Playwright Chromium download fails on ARM) is downgraded from fatal to skip-OK by writing `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` into `.env`; other optional deps that fail to install are listed as non-critical rather than blocking startup. Run it from Termux with `bash launcher_android/start.sh` — the shim handles installing `proot-distro`, the Ubuntu distro, and `textual` inside the proot on first run. See `launcher_android/README.md` for full setup steps and the Browser-bridge mechanism that forwards URLs to Android's `termux-open-url`.

**Android (Termux, TUI manager only):** to install just the standalone **Server Manager TUI** (`TUI/`) on a phone — not the full server — paste one line into Termux:

```
cd ~ && pkg install -y git && git clone --depth 1 https://github.com/botboss3000/webagent ~/webagent && bash ~/webagent/TUI/install-termux.sh
```

…or, using the short public URL the server itself hosts:


The installer (`TUI/install-termux.sh`) installs Python + git and the TUI's lightweight runtime dependencies, then runs the manager directly from source on supported Python 3.11–3.14. It drops a `webagent` command on PATH plus a Termux:Widget home-screen shortcut. The app serves that script verbatim (LF-normalised) at **`/termux`** (and `/termux.sh`). Unlike `launcher_android/` (which runs the whole server under proot), this is just the lightweight manager. See `TUI/README.md`.

## Context defaults (no `/seed-docs` route)

There is **no** `POST /api/v1/seed-docs` in this codebase. When a user has no context rows, the first chat path copies **`context_templates`** into that user’s store (**`public.context`** on Supabase, **`context_documents`** in local SQLite).

## Using the chat API

**`POST /api/v1/chat`**

Minimal JSON body:

```json
{
  "user_id": "auth-user-uuid",
  "session_id": "session-uuid",
  "message": "What can you help me with?"
}
```

**`session_id`** is auto-created if it doesn't exist (first message in a new session creates the row automatically).

Optional fields include **`documents`**, legacy **`history`**, and **`attachment_ids`** (list of UUIDs from prior uploads) — see **`ChatRequest`** in **`app/models/schemas.py`**. When `attachment_ids` are provided, the agent sees a `[USER ATTACHMENTS]` section in its system prompt and can use the **`read_attachment`** tool to inspect file contents. **Model context is rebuilt from `interactions` in the DB** for that `session_id`; you do not need to resend **`history`** after a refresh (it is ignored for the transcript).

Example:

```bash
curl -X POST "http://localhost:8080/api/v1/chat" \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user_123",
    "session_id": "session_456",
    "message": "What can you help me with?"
  }'
```

Response includes **`reply`**, **`response`** (duplicate for different clients), and **`session_id`**. Turns are stored in **`interactions`**.

## Prompt slots and overrides

> For *what* prompts and context are (in plain English), see the Wiki: [Prompts & Context](http://localhost:8080/?tab=wiki&article=prompts-context). This section is the storage-layer reference.

Prompts that shape an agent flow through **three tables**, each with a single, clear job:

| Table | What it holds | Who writes it |
|-------|---------------|---------------|
| **`agent_templates`** | Per-template **config** (model, temperature, max_tokens, loop_logic, trigger). One row per template id (`default`, `admin-agent`, etc.). | JSON seeder |
| **`agent_prompt_templates`** | Canonical **slot content** for each template (system, agent, user, skills, tasks, misc, automation, bootstrap_tools). One row per `(template_id, slot_name)`. Versioned via `version` int + `source` enum (`'json'` \| `'admin'`). | JSON seeder + admin-edit-back UI (planned) |
| **`agent_prompts`** | Per-agent runtime slot rows: the **admin-base rows cloned from the template** when a new agent is created, plus any **per-user override rows**. Each clone stamps `template_version` so the agent can be told "your template moved to v4". | Agent creation + per-user override endpoints |

A new agent is born by:

1. Looking up the template row in `agent_templates` (config).
2. Cloning every row from `agent_prompt_templates WHERE template_id = <template_id>` into `agent_prompts` under the new agent's id (with `user_id IS NULL` and `template_version` stamped from the source row).
3. Any per-user override gets written as an extra row in `agent_prompts` with a non-null `user_id`.

**Admin base** rows in `agent_prompts` carry the slot's policy: `order_index` (where the slot sits in the assembled system message), `lock` (admin-only when true), and `merge_mode` (`replace` or `append`).

**User override** rows have a non-null `user_id`. Each user (including anonymous browser-scoped visitors) can have at most one override per slot. When the agent loop assembles the system prompt for a caller, locked slots ignore overrides; unlocked slots either `replace` the admin base with the user override or `append` it below, per the slot's `merge_mode`.

### Seeding from JSON (manifest-gated, version-aware)

`app/defaults/agents/*.json` (or a `data/agents/` override if present) is the recovery source of truth for fresh databases. See [`app/defaults/agents/README.md`](app/defaults/agents/README.md) for the **full field schema** — every agent-page setting a template can carry (limits, trigger, loop logic, per-tool `tool_modes`/`tool_permissions`), with override-or-default semantics (present overrides the built-in default; missing falls back and never breaks). Each file declares a top-level integer `"version"` that gates the per-slot upsert:

- New slot → insert with `source='json'`, `version=<JSON version>`.
- Existing slot with `source='json'` and JSON version > DB version → update + bump.
- Existing slot with `source='admin'` → **skip** (admin edits are sacred).
- Manifest hash of all JSON files is stored in `app_meta.last_agent_manifest_hash`; the seeder short-circuits when the hash matches, so it's cheap to call at every boot.

The seeder runs at **app startup** (manifest-gated, almost always a no-op). To re-seed on demand or force-overwrite admin edits, use **App Config → Agent Settings → Templates and prompts → Agent Prompt Templates** (`/admin/db/templates`, `POST /admin/db/templates/seed`, `POST /admin/db/templates/seed-force`).

### Endpoints

- **`GET /api/v1/agents/{agent_id}/slots?user_id=...`** — returns the admin-base slot list plus the caller's overrides per slot, and a `user_role` of `"admin"` or `"member"`.
- **`PUT /api/v1/agents/{agent_id}`** (admin only) — agent-row fields plus an optional `slots` array that fully reconciles the admin-base slot set. May include `reset_overrides_for` (list of slot_names) to wipe all per-user overrides for those slots at save time.
- **`PUT /api/v1/agents/{agent_id}/my-prompts`** — any caller writes their own override rows for unlocked slots; locked or unknown slot_names are rejected per item.
- **`DELETE /api/v1/agents/{agent_id}/my-prompts/{slot_name}?user_id=...`** — clears one user's override for a slot.

### Recycling bin (soft delete)

Agents, chat sessions, and automations are never hard-deleted from the normal UI — they go to a recycling bin first. Lifecycle is tracked by a marker column: agents are `active` ↔ `trashed`, sessions are `active` ↔ `recycled`, and the automation surfaces use a nullable **`deleted_at`** (NULL = active, set = binned). Child rows (agent_prompts, interactions) carry no flag of their own; they follow their parent and are erased only on a permanent delete. (`agents.status` already existed and was extended; `sessions.status` was added; `deleted_at` was added to `agent_automations`, `agent_event_subscriptions`, `webhook_registrations`, and the plugin-owned `agent_spawns` (clones reuse `status='clone_trashed'`) — see `app/db/schema/tables.py` and the `local.py` SCHEMA_SQL + ALTER-TABLE migration 030; Postgres picks it up via column reconcile.)

All three pages share one toolbar control — a button that shows a green **recycle** icon when nothing is selected (click it to open the bin) and a red **trash** icon when rows are selected (two-click confirm to move them to the bin, or — inside the bin — to permanently delete). Inside the bin a **Back** link and a **Restore** button appear. (HARMONY: grep `HARMONY-AGENTS-BIN` / `HARMONY-SESSIONS-BIN`.)

- **`GET /api/v1/agents?user_id=...&view=bin`** — lists only the caller's trashed agents (the Agents-page bin view). Default `view=active` lists live agents + visible templates.
- **`DELETE /api/v1/agents/{agent_id}?user_id=...`** — SOFT delete: moves the agent to the bin (`status='trashed'`). Add **`&permanent=true`** to erase it for good (agent + prompts + its sessions + their transcripts/summaries + connections/abilities) — used by the bin's own trash button. Permanent delete also **cascade-removes any clones** the agent's sessions orchestrated (`cascade_delete_clones`; `status='clone'` agents only).
- **`POST /api/v1/agents/{agent_id}/restore?user_id=...`** — restores a trashed agent back to the Agents page.
- **`DELETE /api/v1/db/sessions/{session_id}?db=local.db`** — SOFT delete: recycles the session (`status='recycled'`, hidden from the chat dropdown but kept). Add **`&permanent=true`** to erase it. A recycled session is truly removed only when its agent is permanently emptied from the bin.
- **Automations completed view + bin.** The Automations dashboard (`ui/main-panel/agents/automations/server.py`, embedded in the Agents page) splits its rows into three sibling views via **`?view=`**: `active` (default — only in-process/future automations), **`completed`** (a non-destructive history of automations that have finished for good — one-off tasks that fired, expired/exhausted recurring tasks, and worker spawns in a terminal status; computed at read time by `_is_completed`, never a stored flag, so nothing migrates), and `bin` (the recycling bin). The completed view keeps the main list uncluttered without deleting anything; its toolbar button carries a `completed_count` badge and deleting from it soft-deletes into the bin like the active view. The dashboard recycles all five record types it aggregates. **`GET /api/v1/automations/dashboard?user_id=...&view=bin`** lists the binned rows (default `view=active`). The four `DELETE` routes (`/{id}` for scheduled+event, `/spawn/{id}`, `/clone/{id}`, `/webhook/{id}`) SOFT-delete by default and take **`&permanent=true`** to erase; each has a matching **`POST .../restore`**. Recycling a scheduled task or event sub also sets `enabled=0` (so the scheduler/event engine — which only act on `enabled=1` rows — never fire a binned row, no hot-path change) and mangles its slot `source_hash`; a webhook recycle sets `active=0`. Slot reconciliation (`delete_*_not_in`) skips `deleted_at IS NOT NULL` rows so the bin is never silently purged, and restored rows flip to `origin='dashboard'` so reconciliation leaves them alone.
- **Hidden sessions (declutter, not delete).** Sessions carry a `hidden` flag (`sessions.hidden` INTEGER, default 0 — added via the `local.py` ALTER-TABLE migration, paired with `pinned`). The chat-header dropdown has a **management footer row** (an eye toggle + a delete-all button) — see `ui/chat/js/session-list.js` / `session-init.js`. The eye toggle enters "manage mode": it reveals hidden sessions and swaps each row's trash button for an eye that hides/un-hides that session. **`GET /api/v1/db/sessions`** excludes `hidden=1` rows by default; pass **`&include_hidden=1`** to include them (each session object carries a `hidden` boolean). **`PATCH /api/v1/db/sessions/{session_id}`** now accepts a `hidden` boolean (alongside `title` and `pinned`). The footer **delete-all** spares pinned and hidden sessions and reuses the per-session soft delete.

The Agents-page header (`ui/main-panel/agents/agents.html` + `ui/main-panel/agents/js/agents.js`) renders the bin controls — per-square checkboxes plus **Select all / Deselect all / Trash** (and **Back to Agents / Restore** inside the bin). The trash button moves checked agents to the bin, or — with nothing checked — opens the bin view (a view-swap inside the same Agents tab, not a new nav tab).

### Clones view

The Agents page has a **Clones** tile (to the right of the "New Agent" tile) that opens a read-only view listing ephemeral clone agents created by the Agent Orchestration ability. Clones have `status='clone'` and are hidden from the normal roster and recycling bin. The view groups clones by their orchestrator agent and shows each clone's name, `spawn_status`, and result summary. Use the "Back to Agents" header to return to the normal grid.

- **`GET /api/v1/agents?user_id=...&view=clones`** — lists the caller's `status='clone'` agents, newest first, enriched with spawn-ledger fields (`spawn_status`, `result_summary`, `orchestrator_session_id`, `orchestrator_agent_id`) from the `agent_spawns` table when available.
- The "Clones" tile uses a Lucide `copy` icon with the `color-teal` square style. The clones view shares the same "Back to Agents" toolbar pattern as the recycling bin (grep `RETURN-TO-AGENTS-HEADER` in `ui/`).

### Task delegation to a saved agent

Besides spawning throwaway **clones**, the Agent Orchestration ability can hand a **discrete task to one of the user's own saved agents** — `delegate_task_to_agent(agent, task, wait?)` (discover targets with `list_task_delegatable_agents`). This is distinct from `delegate_to_agent`, which hands the *whole* session over in place. A delegation runs the **real agent as itself** (its own persona, abilities and `metadata.engine`) in a fresh `spawn-…` sub-session bound to that agent — so delegating to a **Local Claude Code** agent makes the task genuinely run through the machine's `claude` CLI (the loop's per-agent engine dispatch keys off the bound agent). It reuses the whole spawn family machinery: the delegation is written to `agent_spawns` with a new **`kind='delegate'`** marker (clone spawns leave `kind` NULL/`'spawn'`), so it counts toward the same orchestration limits, is manageable with the same helper tools (`message_spawn` / `read_spawn` / `quote_spawn` / `stop_spawn` / `schedule_spawn_check`), and surfaces as a **tab in the chat sub-header** next to spawns (the `GET /api/v1/db/sessions/{id}/related` family endpoint emits it with `role='delegate'` and the agent's name; the tab uses a `share-2` icon). The clone-reaper (`_reap_clone_family` in `app/db/local.py`) only ever deletes agent records + agent-scoped data (`agent_prompts` / `agent_connections` / `agent_abilities`) for `status='clone'` agents, so deleting an orchestrator chat cleans up a delegation's sub-session and ledger row but never touches the real delegated agent's config.

### In-chat self-modification

The agent's in-chat prompt-refinement flow uses the same admin/user split: admin callers may write to admin-base rows, members and anonymous visitors can only write to their own override rows. Locked slots are refused with a user-visible message.

## Deployment

> Plain-English version in the Wiki: [Deploying to the Cloud](http://localhost:8080/?tab=wiki&article=deploying-to-the-cloud) and [Editions and the Production Path](http://localhost:8080/?tab=wiki&article=editions-and-the-production-path). ### Google Cloud Run

WebAgent is designed to run on Cloud Run. The `Dockerfile` is Cloud Run-ready (`PORT` env var, health check, CORS).

**Cloud Run compatibility checklist (maintain when changing code):**

| Requirement | Why |
|-------------|-----|
| All new Python deps added to `requirements.txt` | Cloud Run builds from `pip install -r requirements.txt` — missing deps crash at runtime |
| No dependency on persistent local filesystem | Container filesystem is **ephemeral** — use Supabase (cloud mode) for DB, Supabase Storage for uploads |
| WebSocket endpoints accept remote clients | Both `/api/v1/agent/ws` and `/api/v1/terminal/ws` accept connections from any origin (no loopback guard) |
| File writes backed by `git push` | Code changes on ephemeral disk are lost on container recycle — commit and push to persist |
| `WEBAGENT_CONFIG_SOURCE=env` set | Locks storage config to env vars so `db_mode.json` / `db_connection.json` / `secrets_mode.json` writes are suppressed (they would only land on the ephemeral container disk). Provider, host, db, user, and the secrets vault are sourced from env vars instead. |
| Secrets in a real vault | Use `WEBAGENT_SECRETS_PROVIDER=gcp_secret_manager` on GCP (set `GCP_PROJECT`) — never leave passwords in `inline_db` for production. |
| `asyncpg` available | Required when using any Postgres-family provider (Supabase, Postgres, Amazon RDS, Google Cloud SQL, Azure Database, Neon) for connection testing and schema bootstrap. Pinned in `requirements.txt`. |
| `aiomysql` + `sqlglot` available | Required for per-agent external data source connectors. `aiomysql` powers the `sql_mysql` connector; `sqlglot` is used by SQL connectors to parse statement type and referenced tables before sending to the customer DB. Both are pinned in `requirements.txt`. |
| Automation scheduler set to a remote backend on Cloud Run | The default `LocalScheduler` in **`app/scheduler/local.py`** is in-process — it does not survive container recycles and will not fire across multiple instances. For Cloud Run deployments switch the provider to `google_cloud` under **App Config → Agent Settings → Automation Engine** (pushes each job to Google Cloud Scheduler — see **`app/scheduler/providers/google_cloud.py`**). |
| Event-trigger poll + renewer loops are in-process | The loops in **`app/events/poller.py`** and **`app/events/renewer.py`** share the same Cloud Run limitation as the local scheduler — they only run while the container is warm. Push-based event sources (Gmail / Outlook / Calendar / Drive / Dropbox / Shopify / comms bridges) work fine on Cloud Run because providers POST directly to **`/api/v1/events/{source}`** and wake the container; poll-only sources (Twitter, Reddit) need a long-running host (the GCE VM) or an external scheduler that hits the poll endpoints. Subscription renewal also needs a warm instance — if you scale to zero, set `min_instances=1` or invoke a refresh from Cloud Scheduler. |
| Agent Orchestration spawns rely on background work | Forked spawned-helper runners and the orchestration recovery poller (**`plugins/abilities/agent_orchestration.py`**) are in-process background tasks. They need **CPU always allocated** (not request-scoped — otherwise a forked helper is frozen after its request returns) and **`min_instances=1`** (so a poller is always alive to recover spawns orphaned by a recycle; with scale-to-zero, orphans wait until the next request). Recovery **is** multi-instance safe (heartbeat liveness + atomic token claim, so two instances can't re-run the same spawn), but the loopback that runs a spawn always targets the same instance that fired it. Blocking (`wait=true`) spawn chains run inside one request — keep them under the Cloud Run request timeout; prefer forks for long work. Tune throughput with `WEBAGENT_SPAWN_CONCURRENCY`. |
| `doc_store` connector uses Supabase Storage in cloud mode | The local-filesystem variant relies on a writable container path that survives between requests. In Cloud Run that path is ephemeral, so the data-source admin UI hides the `local` backend option when `WEBAGENT_CONFIG_SOURCE=env`. Use `backend: supabase_storage` instead, and apply **`migrations/014_data_sources.sql`** to add the `data_sources`, `agent_data_sources`, and `doc_chunks` tables (plus pgvector + the `doc_chunks_hybrid_search` RPC) before attaching any sources. |

**Deploy (manual):**
```bash
gcloud run deploy webagent \
  --source . \
  --region europe-west1 \
  --allow-unauthenticated
```

### Google Compute Engine VM (persistent disk)

Unlike Cloud Run, a GCE VM has a real, persistent filesystem — so you can keep code under version control on the box itself and pull updates in place from the GitHub tab inside the app.

**One-time VM setup:**

1. **Clone the repo** to a stable path, e.g. `/opt/webagent`, and create the `.venv` + `.env` next to it (same layout as local dev).
2. **Create a dedicated user** for the service (e.g. `webagent`) and `chown -R webagent:webagent /opt/webagent`. The user needs read/write on the repo so the in-app **Pull & Restart** button can run `git pull` and rewrite files.
3. **Install the systemd unit** shipped at **`scripts/webagent.service`**:
   ```bash
   sudo cp /opt/webagent/scripts/webagent.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now webagent
   ```
   Edit `User`, `WorkingDirectory`, `EnvironmentFile`, and the `ExecStart` venv path inside the unit before enabling it if your layout differs.

**Why systemd matters for the GitHub tab’s Pull & Restart button:**

- **`POST /api/v1/restart`** (`app/main.py`) terminates the uvicorn process with `os._exit(0)`.
- The unit file has `Restart=always` / `RestartSec=1`, so systemd immediately relaunches uvicorn from the just-updated source tree.
- Without a supervisor (or with a plain `nohup ./scripts/start_WebAgent.sh &`) the server stays dead after restart and the app becomes unreachable.

**Self-restart that doesn't need a supervisor (`app/relauncher.py`).** For in-app restarts that should *always* come back — e.g. the **Restart server** button on the **App Config → Database → Secrets Vault** panel, offered for a clean vault cutover (`POST /admin/storage/server/restart`, gated by `GET /admin/storage/server/restart-info`) — `trigger_restart()` spawns a tiny detached **relauncher** by file path, then exits the process. The relauncher waits for `/health` to drop, gives any external supervisor (the Server-Manager guardian, a `WebAgent.bat` loop, systemd/launchd) a short head-start to revive the server, and **only relaunches `run.py` itself if nothing else does** — so the server returns even on an unsupervised host, with no duplicate when a supervisor is present (and the guardian's reaper collapses any stray duplicate to the one serving `:8080`). The secrets status (`GET /admin/storage/config` → `secrets.restart_recommended`) flags when the live vault has diverged from the one the process booted with, which is what surfaces that button.

**How updates flow (GCE):**

1. You push code from a dev machine to GitHub.
2. On the VM, in the running app, open the **GitHub** tab as admin — or switch the **File Editor** sidebar to its Source Control view (the GitHub icon next to Explorer).
3. Click **Pull & Restart** — the UI calls `/api/v1/github/pull`, then `/api/v1/restart`, then polls `/health` until the new process is up.
4. Static assets (`ui/`, `index.html`) refresh on the next page reload; Python backend code is now the freshly-pulled version because systemd relaunched uvicorn.

**File Editor sidebar — Source Control view.** The Files tab’s left sidebar has two view modes, toggled by icon buttons at the top:
- **Explorer** (default) — the directory tree. Every row carries a **git change badge** — `+N` (green) / `-N` (red) lines **since the last commit** — so you can see at a glance what's been touched. A **file** shows its own added/removed counts (a brand-new untracked file reads `+N`); a **folder** shows the **sum** of every changed file beneath it, but **only while collapsed** — expand it and the folder's own badge disappears so its now-visible children carry the counts (no double counting). Unchanged rows show nothing. The counts come from `GET /api/v1/github/line-stats`, which returns a repo-relative `path → {added, removed}` map built from `git diff --numstat HEAD` (tracked, staged + unstaged together) plus line counts for untracked files; it is **pinned to this app's own repo** so it always matches the tree regardless of which repo Source Control has selected. The frontend (`ui/shared/js/files.js`) fetches it on tree load, after a file save, and on returning to the Explorer view, then rolls the per-file counts up into folder sums.
- **Source Control** — a compact GitHub manager (status, changes, commit, push/pull, token) plus a VS Code-style commit graph that shows *all* branches/refs (not just `main`). Each row has a coloured lane dot; merge bubbles and side branches render as bent connector lines. The graph is fed by `GET /api/v1/github/log-graph`, which extends `/status` with `git log --all` plus pre-computed lane positions so the frontend just draws SVG segments. Both `/status` and `/log-graph` take an optional `fetch` flag (default `1` = run a live `git fetch` from origin first, so ahead/behind and `origin/*` tips are accurate; `fetch=0` = skip the network round-trip and serve last-known local refs instantly). **Opening the panel uses the fast local-only read (`fetch=0`) so it paints immediately, then refreshes from origin in the background** (a brief "syncing" hint shows on the header) and repaints in place. The **refresh** button (the circular-arrow icon next to **Merge**), and the post commit/push/pull/merge/checkout refreshes, go straight to a live fetch so they reflect origin; refresh repaints *only* this sidebar without touching the rest of the app and spins while loading.
  - **Multiple repos — the repo selector.** A dropdown at the top of the panel chooses **which repo the page acts on**. The built-in **WebAgent (this app)** entry is always first and behaves exactly as before; **Add repository…** registers any other local git folder paired with its own GitHub address + key — the folder field has a **Browse…** picker that walks the host's folders via the existing `GET /api/v1/files/tree`. Picking a repo re-points the **whole page** (Changes list, commit graph, branches, commit/push/pull) at that repo using *its* key; the Production section and the shared-key row hide for non-default repos (each carries its own key, edited from its row). The switch is server-side: the active selection is resolved at the top of every Git endpoint — `_use_active_repo()` re-points the single `_run_git` working dir + token — so the agent's **Git Control** ability is deliberately **pinned** to this app's repo (`_pin_to_project_root()`) and never follows the page's selection. Engine: `app/git_repos.py`; endpoints `GET /api/v1/github/repos`, `GET …/repos/validate`, `POST …/repos`, `POST …/repos/select`, `POST …/repos/{id}`, `DELETE …/repos/{id}`; the list lives in the gitignored `data/config/git-repos.json` (added repos store their own folder/remote/key; the WebAgent entry is synthesized live and never persisted — its `origin` is read from git and its **shared GitHub token now lives in the encrypted vault**, service `deploy_github_token`, the same key the Deploy panel uses, so it's durable and shared across every device on the same vault; `provider.json` is only a local plaintext mirror. `github.py` primes it from the vault at startup + before push/pull/token-status and migrates a legacy `provider.json`-only token in once — see `_prime_shared_token_from_vault`. That same vault row also stores the repo's **clean URL** (`repo_url` in its non-secret config), so a new deployment sharing the vault gets URL + token separately; and cloud deploys reset the deployed box's git `origin` to the clean URL after cloning so the PAT is never baked into it — see [deployment.md](docs/claude/deployment.md) "Reusable GitHub key").
  - **⭐ Instant commit + push.** Next to the commit-message box sits an amber **star** button (enabled when there are uncommitted changes *or* unpushed commits). Clicking it runs the **whole job immediately in a single request** — no chat agent, no waiting through turns. It calls `POST /api/v1/github/commit-and-push`, which stages everything, **auto-writes a commit note from the diff** via a lightweight LLM sub-call (or uses the note typed in the box, if any), runs a **secret-scan safety check** (refuses obvious tokens/keys in the diff), then commits and pushes — reporting the note, hash, and push result inline in the sidebar. **Live progress:** with `stream: true` the endpoint emits newline-delimited JSON phase events (`analyzing` → `scanning` → `message` → `committing` → `pushing`, then a final `done` with the result), so the button shows **granular live status** — a spinner over the button, a stepped status line, and a green check on success — and surfaces a note when the AI message-writer was unavailable and the deterministic file-list summary was used instead. Without the flag it runs to completion and returns a single result dict (the agent-tool path); the frontend also degrades to that automatically if the server doesn't stream. The auto-writer retries a couple of times on a fast failure (empty reply / connection blip) but never waits through a timeout, and its deterministic fallback **title degrades gracefully** (names files → summarises by area) rather than collapsing to a bare "update N files". The shared core (`app/api/github.py` → `_commit_and_push_events`, drained by `commit_and_push_repo`) also backs the **Git Control** ability's `commit_and_push` agent tool (`plugins/admin/source_tools.py`), so the button and the agent tool can't drift. Frontend wiring: `ui/shared/js/files-git.js` (`runCommitFlow`, shared by the ⭐ and plain **Commit** buttons; the NDJSON reader is `streamCommitPush`). All git calls route through the same `_run_git` helper the Push button uses, so auth is identical.
  - **Production (trimmed mirror) — "Release to production".** Below Sync, a **Production** section publishes a *trimmed copy* of this repo to a **separate** GitHub repo (its own folder + remote + history) — everything except the folders **and files** an admin marks **dev-only** in the **File Explorer**. The explorer's toolbar **More** menu (⋯) holds the production tools: *Show dev checkboxes* enters *production-preview* mode — a checkbox appears on every folder and file (ticked = ships, untick = dev-only); unticking a folder dims + locks everything beneath it, and a right-click *Exclude / Include from production* does the same for a single item. **Folder checkboxes are tri-state** — a partial (dash) tick means *some* items inside are dev-only; clicking a partial folder includes its whole subtree, clicking it again excludes the whole folder (all-on → all-off). Git can't push "everything except folder X", so production is regenerated on demand: list the project's real files (`git ls-files`, so `.gitignore` is honoured), drop the excluded paths, mirror the rest into the production repo (wiping all but its `.git` so deletions propagate), secret-scan, **auto-write the release note**, then commit + push — streamed as NDJSON like the ⭐ button. **The release note auto-writes exactly like the ⭐ commit&push:** a blank note (the File Explorer's Sync/Push always leave it blank; the Git page's *Release note* field can override it) triggers the *same* lightweight LLM writer (`_generate_commit_message`), fed the production repo's already-staged diff, so a release gets a real conventional-commit summary of what changed — falling back to the deterministic *"Release from dev … — N files"* line if the writer is down; the stream's `message` → `message_ready` / `message_fallback` phases mirror the ⭐ button's so both surfaces show the same "writing a release message…" step and the written title. The engine is **two composable halves** so the same work runs as one click or as two steps: **sync/copy** (build the trimmed tree in the sister folder + commit it there *locally*, no push) and **push** (send that commit to the production remote). The Git page's **Release** button runs copy-then-push back-to-back; the explorer's **More** menu exposes the halves separately as **Sync to production** and **Push to GitHub** (so an admin can stage and review before publishing). At the top of that menu are **three fields** — **Production repo** (the destination GitHub remote; accepts an `owner/repo` shorthand that's expanded to a full `https://github.com/owner/repo.git` on save, and shows the friendly short form, e.g. `botboss3000/webagent`), **GitHub key** (the personal-access / fine-grained token used to push to that repo) and **Production folder** (the local destination, defaulting to a sibling of the dev repo — `…-dev` → `…-prod`, e.g. `webagent-prod`) — plus a live **in-sync line** that, when the menu opens, compares the dev shipping set against the production folder and reports the result (*In sync — production matches dev* or *Differs: N to add, N to update, N to remove*; *Not synced yet* before the first sync). **The key is a secret, so it goes to the encrypted vault, not the local config** — it's stored in `auth_elements.secret_ref` (per-tenant Fernet when field encryption is on; the same store the deploy panel uses, keyed by service `production_mirror`), the field is **masked, never pre-filled, and never echoed back**, and a **blank value leaves the stored key unchanged** (the config GET returns only a `token_set` boolean). When no production key is stored the engine falls back to the shared Git-page token (now vault-backed — service `deploy_github_token`, resolved via `git_repos.builtin_token()`, with the `provider.json` mirror as a last resort), so existing setups keep working with no key entered; the repo + folder still save to the local config. **Sync to production** is a *one-way sync* of the shipping set from dev into the production folder — it copies new/changed files and drops files no longer shipped — then commits locally. The first sync clones the existing remote (one-time, ~20s — the status line says so); the secret-scan **blocks** the sync if a key/token is found in the shipping set (mark that file dev-only or remove the secret, then retry). First setup is non-destructive (it **clones** an existing remote so the mirror commits on top; only an empty remote gets a fresh `init`). Engine: `app/production_mirror.py` (`copy_events` / `push_events` / `release_events` / `diff_status` + `_normalize_remote_url` + `_auto_commit_message` (reuses the ⭐ button's LLM writer) + the vault helpers `save_vault_token` / `get_vault_token` / `_resolve_token`); endpoints `GET/POST /api/v1/github/production/{config,exclude}` (config POST takes `github_token` → vault; config GET returns `token_set`), `POST …/exclude-bulk`, `GET …/status`, `GET …/diff`, `POST …/{release,copy,push}`; non-secret settings in the gitignored `data/config/production-mirror.json`, the production **key** in the encrypted vault (and the shared `provider.json` token as the fallback).

**Troubleshooting:**
- `journalctl -u webagent -f` — live logs from the unit.
- If Pull & Restart hangs at "Waiting for relaunch…": systemd isn’t restarting the process. Check `systemctl status webagent` and verify `Restart=always` is set.
- If `git pull` fails with auth errors: set a GitHub Personal Access Token via the GitHub tab → Settings (stored in `provider.json` under the service user’s home / repo dir).

## Maintenance

### Resetting local state (`reset_webagent.bat`)

Use **`reset_webagent.bat`** (repo root, Windows) to wipe WebAgent back to a clean state in one go. Intended for local dev — handy when prepping a clean handoff, reproducing a first-run bug, or escaping a corrupted local DB. Double-click or run from a terminal.

**What runs automatically (no prompt):**

1. **Stops the running app** — kills any process on port 8080 plus `python.exe` / `python3.exe`, the same pattern as `kill_webagent.bat`. This is required so the SQLite WAL isn't held open during deletion.
2. **Wipes the userbase** — the database files (`data\db\local.db` plus `-journal`, `-wal`, `-shm`, `.preprompt-bak`, and any stray root-level `local.db`) and the per-user generated pages directory (`visuals\users\`). Credentials (`data\db\vault.db`), the LLM key/config, and logins are preserved unless their opt-in group is selected; the diagnostics logs (`data\db\logs.db`, `recordings.db`) are kept unless explicitly cleared. The DB schema, the default `admin / admin` user, and the agent templates are all re-seeded automatically on the next `WebAgent.bat` start (see `_init_db()` and `_seed_agent_templates_from_json_files()` in `app/db/local.py`, and `_ensure_default_admin()` in `app/auth/users.py`).

**Prompts (in order):**

| # | Prompt | Default | Targets when "yes" |
|---|--------|---------|---------------------|
| 1 | Back up files to `temp\reset-backup-<timestamp>\` before deleting? | **Yes** | Every targeted file/folder is `move`d into a timestamped folder under `temp\` mirroring its original path (reversible). On "No", everything is hard-deleted via `del /F /Q` or `rmdir /S /Q`. |
| 2 | Clear app secrets (LLM API keys, OAuth tokens, integration creds, scheduler config)? | No | `data/config/provider.json`, `data/config/app-settings.json`, `data/config/scheduler_config.json`, `app\db_mode.json`, `app\pages_mode.json`, `app\db_connection.json`, `app\secrets_mode.json`. App falls back to local defaults when these are missing. |
| 3 | Clear local user accounts (passwords, remember-me tokens)? | No | `app\auth\users.json`, `app\auth\users.json.bak`. **Note:** accounts now live in the shared DB's `user_accounts` table, so these files are only the pre-migration backup — clearing them no longer removes DB accounts. Reset the `user_accounts` rows via the Data Settings DB reset (or re-run setup) to clear the live store. |
| 4 | Delete `.env`? | **No** | `.env` at repo root. Default No — most installs (Supabase, OAuth client IDs) need this file to start. |
| 5 | Delete agent template JSON files in `app\context\agents\`? | No | All `*.json` under `app\context\agents\`. **Warning:** there is no fallback — the next start will boot with zero agents until you restore templates. |
| — | Final **Proceed? [y/N]** summary lists every path that will be processed, tagged `[BACKUP]` or `[DELETE]`. Defaults to No (abort). | No | — |

After execution the script prints `OK` / `FAIL` / `SKIPPED` counts and (if backups were enabled) the backup path. Run `WebAgent.bat` afterwards to relaunch from a clean install.

**Related scripts:** `WebAgent.bat` (start + auto-restart), `kill_webagent.bat` (stop-only), `export_agent_templates.bat` (reverse-seed: DB → JSON templates).
