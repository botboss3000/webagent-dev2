# V3 development release workflow

Use one stable task ID per source change. Call `v3_build_work(action="begin", mode="isolated", task_id=..., summary=...)` before editing. The receipt gives a private task workspace and its input digest. Other tasks may stay open or build while this task is edited. Use a seeded V3 source workspace for code work, review its complete text diff, then call `v3_source_apply` with that diff, the task ID, a stable request ID, and the task workspace digest from `v3_build_work.status`. The broker checks paths, digest and `git apply --check` before patching only this task's snapshot. Inspect `v3_source_receipt` after an uncertain apply; never create a second request ID to retry an uncertain write.

Run focused checks against the reviewed task source. After edits settle, read `v3_build_work.status` again and use that task's `workspace_inputs_sha256` in `finish`. Finishing freezes this task's source and immediately assigns its own durable job ID. Changes only under `v3/ui/` use a UI release: the broker stages the frozen source without Cargo or Buildx. After the stable asset mount is installed, it switches the UI snapshot while the containers keep running, including during a Rust image build. The initial mount migration reuses running images with a brief container replacement. Rust test status for UI jobs is `not_required`.

Compatible queued full-build tasks from one caller may be merged before compilation, up to eight tasks per image build. Each retains its own durable job ID and receives the shared tested-build result. A started image build stays frozen. If a UI release finishes during it, the broker checks that non-UI inputs are identical, then rebases its candidate onto the new UI snapshot before deployment. A same-file conflict fails the conflicting task; use a new task from the current release to revise it. A task ID is single use.

The original `finish` tool call remains pending while the Rust loop waits for the durable job. After a loop restart, base recovery reads the broker receipt and returns one terminal result on that same call ID; do not submit `finish` again.

The API serves UI assets and seeds new coding workspaces from a broker-owned, versioned source snapshot behind a stable read-only mount. The broker atomically selects the complete snapshot and verifies the served UI. Runtime code, config and abilities stay pinned to their tested container release. Edits in another task workspace or the writable File Manager checkout cannot change mounted release assets. Only the broker chooses development targets; production is never a target. An uncertain external effect blocks subsequent releases until reconciliation.

After both replacements are healthy, the broker promotes changed release files
into the shared checkout if those paths still match the prior or new release.
A conflicting direct checkout edit holds subsequent releases for reconciliation.

Wait for the original `finish` result, which includes the terminal job status, phase, bounded reason or log excerpt, job ID, and final container health. The Rust recovery watcher reads the broker internally while the agent is idle. If the result cannot be delivered because recovery is stopped or broker access is unavailable, inspect the existing task and job read only; never submit a duplicate build. Approval and live automatic-deployment policy are required when finishing; revocation stops queued or running work. Abandon only an open task whose edits are no longer intended for release.

After a completed release is healthy and its changed files have been promoted to the shared checkout, attempt to commit and push only those source changes to `main`. First inspect `git status --short --branch`, the exact task diff, and the index. Proceed only if the branch is `main`, the index has no other writer's staged changes, and the task's paths can be identified exactly. Stage those paths only, review `git diff --cached`, commit, then use a normal `git push origin main`. Never use `git add -A`, force push, rewrite history, or include runtime data, secrets, or another task's edits. If Git permissions, conflicts, divergence, or ownership prevent this, report the failure and leave the source intact. A push is a source backup; it does not require retaining generated image archives.

Check development storage after each terminal build, including a successful UI release. From the server use `df -h /`, `docker system df`, and `python3 -B /home/ar/webagent-dev2/scripts/dev_artifact_prune.py --dry-run`. After a healthy completed release, run `sudo systemctl start webagent-dev-artifact-prune.service` and check `df -h /` again. This service also runs when build receipts change and about every ten minutes. It clears completed or superseded development rollback tars, old stopped V3 containers and images, finished check caches, aged V2 temporary builds, unused development volumes, Docker build cache above 50 GiB root use, and protected root-owned rollback copies after one hour. It retains the current mounted release, open check tasks, active compiler output, application state, workspaces, and unresolved newer job receipts. If root use stays above 50 GiB, inspect the measured development directories and report the remaining owners; do not run a host-wide prune or operate on production containers.

The dry run cannot see the root-owned protected copies. Include `sudo du -sh /home/ar/webagent-dev2/v3/rollback/administrator` in the storage check, and inspect the service result with `sudo systemctl status webagent-dev-artifact-prune.service` if cleanup fails.

Codex uses the same broker through server-side `buildctl.py`: `begin` defaults to an isolated workspace, `inputs --task ID` reads its digest, `finish ID --expected DIGEST` queues one release, and `wait ID` polls without creating a job. The V2 Python bridge uses the same task registry and its own authenticated caller identity. Legacy shared-checkout work must not overlap isolated tasks.
