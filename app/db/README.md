the system_prompt is hardcoded to use the system_prompt.md as fallback. the priority prompt is loaded through the database.

The Phase 1 browser authority/cache contract, retention policy, benchmark, and
Phase 2 handoff are documented in `docs/storage-authority-phase1.md`.

Storage layout v2 assigns every core table to an app, user, agent, secrets, or
telemetry authority in `schema/ownership.py`. See
`docs/storage-layout-v2.md` for generated schemas and the hard-cutover rules.

SQLite remains the **zero-config default**, but it is plane-routed: app data is
in `data/db/app.db`, user data is in `data/user_data/<user>/<user>.db`, and each
agent is authoritative in its own `data/agent_data/` database. `local.db` and
`global.db` are retired and are never runtime fallbacks. Remote deployments can
still use a Postgres-family backend through the same `StorageBackend` interface.

## SQLite write concurrency (tuned for parallel agent writes)

SQLite allows only **one writer at a time** for the whole file, so the design serialises writes two ways and then makes each write commit as fast as possible:

1. **In-process serialisation** — every write method takes `LocalBackend._write_lock` (an `asyncio.Lock`). The app is single-process / single-event-loop, so this funnels all writes through one queue instead of letting many connections collide and throw `database is locked`.
2. **Fast commits** — `_get_conn()` opens each connection with a tuned PRAGMA set: `journal_mode=WAL` (readers never block the writer), **`synchronous=NORMAL`** (the big throughput win — no fsync per commit; crash-safe in WAL, only a hard power-loss can drop the last not-yet-checkpointed transactions), `busy_timeout=30000`, `temp_store=MEMORY`, `cache_size=-16000` (~16 MB), `mmap_size=256MB`, `wal_autocheckpoint=2000`. See the docstring on `_get_conn()` for the rationale per pragma.

Durability trade-off: with `synchronous=NORMAL`, a sudden power loss / OS crash can lose the **last few committed transactions** that hadn't been checkpointed yet — but the database is **never corrupted**. Acceptable for the agent harness (interactions / diagnostics / stream chunks); revisit if a table ever needs hard durability.

## Credentials vault — `vault.db` (always local, separate from user data)

`auth_elements` (per-user service credentials: integration **OAuth tokens** + the **inline secret values** stored by `InlineDBSecrets`, plus the LLM auth row) does **not** live in the user-data `local.db`. It lives in a dedicated sibling file **`data/db/vault.db`**, so a user-data reset never wipes credentials — the app keeps working after a reset.

How it works (SQLite only, zero call-site changes):

- `LocalBackend._get_conn()` **`ATTACH`es** `vault.db` as the `vault` schema on every connection.
- `auth_elements` is **removed from the main SQLite schema** (`SCHEMA_SQL`) and created **only in the vault** (`VAULT_SCHEMA`). With the table absent from `main`, SQLite's main-first name resolution makes every unqualified `… FROM auth_elements` query — in the backend methods, the raw-client query builder (`get_raw_client`), and the encryption migration — resolve transparently to the vault. No per-call-site edits.
- On init, a **one-time migration** copies any legacy `main.auth_elements` rows into the vault (explicit columns + `COALESCE` so NULL-default rows can't be silently dropped) and only **drops the source once every row is confirmed copied** (a partial copy leaves the main table in place — safe fallback, retried next boot).
- The vault path pairs `local.db` → `vault.db`; any other DB file → `<name>.vault.db` (so test / reference instances get isolated vaults).

**Postgres:** the vault is a SQLite-file concept. `PostgresBackend` overrides `_get_conn` (no ATTACH) and `auth_elements` stays a normal table in the Postgres schema (`tables.py` / `render_postgres`). Caveat: a Postgres **schema-drop reset wipes `auth_elements` too** (it's in the dropped schema), and `migrate_sqlite_to_pg` reads `local.db` only, so it currently won't carry `vault.db` rows across — both are follow-ups for Postgres deployments. `vault.db` is a **gitignored runtime artifact**.

## DB-connection credential store — `cred_store.py` (keyring, NOT the database)

The credentials *vault* above (`auth_elements`) lives **inside the database**. That is fine for app secrets, but it is circular for the secrets that open a **remote** database connection: a Postgres password stored in the `inline_db` vault would live in the very database the password is needed to reach. When that DB is down — or on any cold start — the password is unreachable and the app silently drops to local SQLite. That is exactly how a device configured for a shared DB quietly stops sharing it.

`db/cred_store.py` solves this. It is a small, **synchronous, database-independent** store for *only* the connection-opening secrets (Postgres password keyed `db_password_<provider>`, Supabase service key keyed `supabase_service_key`):

- **Primary store:** the OS keyring (service `webagent_db`) — Windows Credential Manager / macOS Keychain / Linux Secret Service.
- **Fallback:** a 0600 `~/.webagent/db_creds.json` (outside the repo, like the per-machine `device_id`) on headless hosts with no usable keyring; logged as a plaintext downgrade.
- **Save / Activate** (`app/admin/storage.py`) write here authoritatively, and **self-heal** older installs by copying a secret found only in the legacy `app.secrets` vault across to the keyring. The legacy vault write is kept as a best-effort secondary so the admin Secrets UI still lists it.
- **Cold start** (`get_db()` → `_resolve_pg_password` / `_hydrate_supabase_env_sync`) reads here with **no event loop** (keyring is sync), and tries the conventional `db_password_<provider>` name even when `password_secret_key` is null, so a config missing the key reference still resolves.

## Connection health — `get_connection_health()` (no more silent fallback)

When `get_db()` can't reach the shared database the admin signed into, it still has to return *something*, so it drops to this device's local SQLite copy. The catch: that local copy **always probes green**, so the failure used to be invisible — a device would quietly read a different `device_presence` table and "see" the wrong set of devices.

`db/__init__.py` now keeps a small in-memory **health record** (`_conn_health`, read via `get_connection_health()`). `get_db()` decides the intended backend from the **saved connection-config provider** (Postgres-family / Supabase / SQLite), and on every fallback to local calls `_mark_degraded(intended, reason, detail)`; on success or an *intentional* local-SQLite choice it calls `_mark_healthy(...)`. Fields: `degraded`, `intended`, `actual`, `reason` (`no_password` / `no_credentials` / `connect_failed`), `detail` (the underlying error), and a ready-to-show `message`. First-run local (no remote ever configured) stays healthy so there is no false alarm.

The Instances page (`ui/main-panel/app/`) reads this in its `/admin/instances/backend-status` and renders a red "Not connected to the shared database" banner with a one-click jump to the sign-in form, instead of the misleading green "Connected".

## Pluggable backends + the Postgres translation layer

`PostgresBackend` (in `postgres_backend.py`) is a **subclass of `LocalBackend`** that overrides only the connection and schema bootstrap. Every data method is inherited and runs through **`pg_portable.py`** — a `sqlite3`-compatible facade over a pooled `psycopg` connection that translates SQLite-dialect SQL to Postgres on the fly (`?`→`%s`, `INSERT OR IGNORE/REPLACE`→`ON CONFLICT`, `datetime('now')`→text timestamp, `IFNULL`→`COALESCE`, `json_each(col)`→`json_array_elements_text(...)`). This means **one codebase serves both stores** — when writing new backend code, keep using `self._get_conn()` + SQLite-dialect SQL and it works on both. Avoid Postgres-only or SQLite-only SQL in shared methods; if a method genuinely needs native features (FTS, embeddings), override it in `PostgresBackend` (see `_fts5_search`, `_vector_search`, `doc_chunk_upsert`).

Parity rules for the Postgres schema (`ddl_renderer.py`): `TIMESTAMP` and `JSON` columns render as **TEXT** (the app stores ISO strings / `json.dumps` text and reads them back as strings — JSONB/timestamptz would hand back parsed objects and break callers). The one native type is **`VECTOR`** (pgvector `vector(1536)`) for embeddings. Tables are emitted in **foreign-key dependency order** (Postgres enforces FK targets at CREATE time; SQLite doesn't).

**Row Level Security (Postgres only):** immediately after each CREATE TABLE the renderer emits a three-statement lock (`_render_rls`): `ALTER TABLE <t> ENABLE ROW LEVEL SECURITY;`, then `DROP POLICY IF EXISTS <t>_no_public_access …` + `CREATE POLICY <t>_no_public_access … AS PERMISSIVE FOR ALL TO public USING (false) WITH CHECK (false);`. This is a **deny-by-default lock**, not row filtering: a role that doesn't bypass RLS (Supabase's public `anon`/`authenticated` keys) is refused all access (`USING (false)` grants nothing), while the role WebAgent actually connects with keeps full access — Supabase's `service_role` is a BYPASSRLS role, and a self-hosted table owner bypasses RLS by default. So the app is unaffected on both backends. The **policy** (not just the enable) is what clears Supabase's *softer* "RLS enabled, no policy" advisor note as well as the "RLS disabled in public" error; it's co-located with each table so Supabase's SQL-editor pre-run check sees the lock next to the table it guards. **Two render variants (`idempotent` flag on `render_postgres`/`render`):** every *execution* path (`postgres_backend.bootstrap_schema`, the startup `_bootstrap_pg_schema`) renders `idempotent=True` — `CREATE TABLE IF NOT EXISTS` + `DROP POLICY IF EXISTS`-guarded `CREATE POLICY` — so re-runs are safe (each statement runs independently via `_iter_ddl_statements`; a per-statement failure is logged and skipped). The **Supabase SQL-Editor copy** (`/db/schema-sql` with `idempotent=False`, sent only for the `supabase` provider by `storage.js`) renders a clean **one-time-setup** script: plain `CREATE TABLE` (no `IF NOT EXISTS`) and `CREATE POLICY` with **no** `DROP`. Reason: Supabase's pre-run linter (a) misreads `CREATE TABLE IF NOT EXISTS x` as a table literally named `IF` and warns it has no RLS, and (b) flags any `DROP` as a "destructive operation". The clean variant avoids both, so the SQL-Editor raises **no** pre-run warnings — at the cost of not being re-runnable (delete existing tables before re-running). The post-run dashboard Advisor (the authoritative check) is clean either way. The project setting Authentication → Policies → "Enable RLS on new tables" is the off-switch for the generic pre-run pop-up.

**Important — every `IF NOT EXISTS` must go in the clean variant, not just on tables.** Supabase's pre-run linter reads the word after `CREATE` as an object name, so `CREATE TABLE IF NOT EXISTS x` **and** `CREATE INDEX IF NOT EXISTS y` both make it report a table named `IF` lacking RLS ("...may be able to access IF"). `idempotent=False` therefore strips `IF NOT EXISTS` from tables **and** indexes/FTS (`_render_index`, `_render_fts_postgres`). Keep any future idempotent guard behind the flag.

**Version stamp:** `SCHEMA_SQL_VERSION` (top of `ddl_renderer.py`) is stamped into the first comment line of every rendered script (`-- WebAgent schema SQL | version … | dialect … | <variant>`). Bump it when the rendered SQL changes; it lets a copied SQL blob be identified at a glance — chiefly to tell a freshly-served script from a stale browser-cached copy. Keep that comment line free of the literal tokens a naive linter scans for (`CREATE TABLE`, `IF`+`EXISTS`, `DROP`) so the header itself can't trip the pre-run check.

**`/db/schema-sql` defaults to `idempotent=False`.** This endpoint is display/copy only (never an execution path — the live bootstrap calls `render_postgres()` directly, defaulting to `True`). The current frontend sends `True` for non-Supabase and `False` for Supabase, but an **older cached frontend** may send no flag; defaulting the endpoint to `False` guarantees the Supabase copy stays clean even against a stale cache. Trade-off: a non-Supabase "Show Schema SQL" copy requested by a flag-less cache is non-re-runnable (cosmetic).

`PostgresBackend._init_db()` renders the schema, then **reconciles columns** against a throwaway no-seed SQLite reference instance — any column added by a future SQLite `ALTER` migration is auto-added to Postgres, so the two never drift.

Copy data with `python -m app.db.migrate_sqlite_to_pg` (see `migrate_sqlite_to_pg.py`).

**Still SQLite-only even under Postgres:** the optimizer self-improvement subsystem (`app/optimizer/`, `app/tools/optimizer_tools.py` — temp `.db` scratch files). The admin DB Viewer (`app/api/db_viewer.py`) is now backend-aware (routes the main DB to Postgres via `_open()` + a standalone autocommit `PgPortableConnection`; temp `.db` files stay SQLite).

## Hybrid local-first backend — `hybrid.py` + `sync/` (ON by default)

`HybridBackend` decorates a **`(local SQLite, remote Postgres)` pair** — the same duck-typed decorator shape as `EncryptedStorageBackend` (it does **not** inherit the `StorageBackend` ABC; `__getattr__` delegates). `get_db()` wraps a reachable Postgres remote with it unless `app/db_hybrid.json` (`{"enabled": false}`) or env `WEBAGENT_DB_HYBRID` explicitly turns it off (absent = on). On a local-only install it is a strict no-op. Composition order is **`Enc(Hybrid(local, remote))`** — encryption stays outermost so field-level secret encryption still sees one backend and authoritative `auth_element_*` reads resolve against the remote.

**Correct-by-default routing.** Every method not explicitly overridden delegates to the **remote authority** — i.e. today's behaviour when Postgres is active. That means money / identity / coordination (billing, `usage_events`, `wallets`, `run_state_*`, interrupts, `background_leader`, `device_*`, `user_profiles`/`is_user_admin`, `auth_element_*`) resolve against Postgres and are **never** sourced from the forgeable local copy. Localizing a method is an opt-in override, so a new method is safe by default.

**The `interactions` split — local-first transcript (the main win).** Phase-0 measurement (`temp/phase0_measure.py`) found the transcript is 46.6 MB and its `input` column alone is 44.9 MB — 99 % fat. The hybrid now writes the **full** interaction row (content + fat `input`/`output`) to the **local** `interactions` table, which is the **source of truth for reads** — `fetch_interactions`/`fetch_first_user_messages` read from SQLite (with a remote fallback if a mirror hiccup left the session out of local). On first touch of a session, its row + existing transcript are pulled from the remote into SQLite (`_ensure_local_session`, "warm on chat open"), so history is present locally; NULL-valued remote keys are dropped so local NOT-NULL defaults apply. The remote authority holds only the **skeleton** (order, roles, tool names, ids, timings, small inline values): the fat `input`/`output` **over a size gate** (`_FAT_THRESHOLD_CHARS`, 2 KB) are stripped to NULL on the remote, so a small value rides along inline but a whale never leaves the device. There is **no side-table** — the local `interactions` table holds everything. Another device sees the skeleton only for rows it didn't run (handoff §7). Diagnostics/recordings are already always-local via `logs_store.py`, so they need no hybrid routing.

**Writes are local-first + background push (Stage 2).** `insert_interaction`/`insert_interactions_batch`/`update_interaction` mint the id **locally**, write the full row to SQLite, and enqueue it in the local **outbox** — **no network on the write path**, so a turn never waits on the remote. The remote receives the stripped skeleton a few seconds later when the background engine drains the queue.

**Agent config is pre-cached on chat open (Stage 3).** An agent's config (its `agents` row + `agent_prompts` slots) is needed at chat-open and every turn but is centrally authored and mutable, so the hybrid keeps a **warm local replica** and serves the config reads (`get_agent_by_id`, `fetch_agent_by_id_with_context`, `resolve_prompts`, `assemble_prompt`) from local — gated by a cheap **version stamp**: `_agent_config_stamp()` does ONE round-trip for the newest `updated_at` across the agent's config rows; if it matches the last-mirrored stamp the heavy config is served from local with no further network, otherwise `_mirror_agent_config()` pulls the bundle fresh (prompt slots replaced wholesale so deletions propagate). The stamp check is TTL-cached (`_AGENT_STAMP_TTL`, 5 s) so the several config reads in one turn collapse to a single verification. Authority stays remote (writes delegate there and bump the stamp, which refreshes us); bounded ~5 s staleness is acceptable for Synced-tier config (handoff §8/§9). `fetch_agent_with_context` (the no-id "any agent" lookup) stays remote.

**Sync engine (`db/sync/`).** A local **outbox** (`outbox.py`, table `hybrid_outbox`) queues writes; `engine.py`'s **pusher** drains it to the remote in coalesced batches (repeated edits to one row → one push, latest wins). Each `SYNCED_SPECS` entry declares its `key`, `watermark`, `fat_cols`+`strip_over` (columns nulled on the remote skeleton above the gate), and `push_only` (pushed, never pulled). `interactions` is a **push-only** spec (`fat_cols=('input','output')`, gate 2 KB) because it has no per-row `updated_at` and its reads come from the warm-on-open mirror, not the puller. The **puller** brings the other Synced tables (`sessions`, `session_summaries`, `session_summary_segments`, `genui`, `webhook_registrations`, `agent_automations`, `agent_event_subscriptions`, plus `agents` and `session_runs` — see the chat-panel section below) back into the local replica using an `updated_at` **watermark** (last-writer-wins). It drops NULL-valued keys before the local upsert so a real remote row's NULLs fall back to the stricter local schema's defaults (same policy as the warm-on-open mirror) instead of tripping a NOT-NULL constraint. **Idle round-trip suppression (adaptive backoff):** every pull is a remote round-trip even when nothing changed, and a permanently-empty table (no local watermark) used to do an unfiltered `SELECT * … LIMIT 500` full scan *every tick forever* — so a table that returns nothing for `WEBAGENT_SYNC_QUIET_AFTER` (default 3) consecutive ticks is only re-checked every `WEBAGENT_SYNC_QUIET_SECONDS` (default 15s) while the engine is idle, dropping the steady-state background tax from ~10 round-trips/tick to ~1-2. The backoff keys on "did this pull return rows", so any table with real cross-device activity resets itself to eager (e.g. a viewer's `session_runs` stays live while a remote turn streams because each pull keeps returning the advancing row), and it's bypassed entirely while a live turn is pushing. A `WEBAGENT_SYNC_STARTUP_DELAY` (default 5s) holds the first full sweep after start so it doesn't compete with the first page-load API burst. Money/coordination never pass through here. A separate **tombstone channel** (`tombstones.py`, table `hybrid_tombstones`) carries HARD deletes the watermark pull can't: a permanently-deleted `sessions`/`agents` row is simply absent from the remote, so the puller can never learn it was erased — instead the deleting device records a tombstone (table+row_id+`deleted_at`) and every peer's `pull_tombstones` reads new ones on the `deleted_at` watermark and applies the matching local delete (cascading a session/agent to its transcript), keeping a local copy so the watermark survives restart. Deletes are applied AFTER the upsert pulls each tick so a delete wins over a same-tick stale upsert. A **resurrection guard** stops a deleted row coming back: before the pusher upserts a `sessions`/`agents` row it checks the remote tombstone table and skips any tombstoned id (otherwise a queued mark-read/rename on one device that raced a permanent delete on another would re-create the row remotely and bounce it back everywhere); applying a tombstone also clears that id from the local outbox. When a tombstone lands, the engine fires a `session_deleted` WS event (and `agent_deleted` for an agent) to the row's owner so an open chat on this device drops its transcript and shows "Session not found" in real time. The engine is backend-agnostic (portable raw-client `select/in_/gt/order/upsert` builder). **Status (Stage 4):** the engine is **started in the app lifespan** (`app/main.py` `startup`/`shutdown`) when the hybrid is enabled, **push + pull** (`pull_enabled=True`). The puller was turned on after the **security audit**: `HybridBackend` serves ONLY the transcript + agent-config reads from local; every money/identity/authorization read falls through to the remote authority. The one authorization value that had leaked into a locally-served path — the agent `user_mode` selector in `chat._enforce_agent_access_policy` — now reads straight from the authority (`db._get_conn()`), and the audit is codified as a guard test (`test_stage4` asserts no sensitive method is overridden). It binds to this machine's local outbox, so it runs per-process (not via the cluster leader). Covered by `temp/test_hybrid.py` (two-SQLite harness + audit-as-code guard) and `temp/verify_stage2_live.py` / `temp/verify_stage4_live.py` (self-cleaning live Supabase checks).

**Chat-panel local reads + optimistic writes (Stage 5).** The agent send/reply path was already local-first, but the **chat side-panel** still read/wrote the remote authority through `app/api/db_viewer.py`, which opened a fresh remote connection per request — so opening a session, switching sessions, and the session dropdown all paid network latency even though the data was on disk. Now, when hybrid is on, the panel's high-value reads are served from the local mirror:

- **`_open_read(db)`** (db_viewer) returns the LOCAL SQLite connection for the main DB when hybrid is enabled, else the normal `_open`. The **session list** (`/db/sessions`), **transcript** (`/db/session-messages`), and the **live-reconcile tail** (`/db/session-tail`) use it. `session-messages` probes for a local row and falls back to the remote for a session not yet mirrored on this device; `list_sessions` falls back to remote until the first puller tick warms `agents` (its agent JOIN would otherwise hide agent-bound sessions). The **tail** now reads local too (so the live poll is CONSISTENT with the initial load instead of racing the remote's ~1 s sync lag — the two disagreeing was the source of the message-flicker), but because `interactions` is **push-only** (a viewer on another machine never pulls another device's live rows) it falls back to the authority — decided from LOCAL reads only, so a normal poll pays no round-trip — when either (a) the session has **no local rows** (cold viewer) or (b) a run is **`running` whose `assistant_interaction_id` row isn't local** (a run streaming on another machine). The narrow residual — a foreign message written AND completed entirely between two idle polls on a *different* machine — surfaces on the next run or reload; single-device and active cross-device stay exact. **Related/family** (`/db/sessions/{id}/related`) stays on the authority (it reads the un-mirrored `agent_spawns`/`browser_sessions`).
- To make the panel's list read correct, the puller now also mirrors **`agents`** (powers the agents dropdown + Agents page roster; `HybridBackend.list_agents_for_user` serves it local-first — a DISPLAY list, never an authz gate; access enforcement stays remote) and **`session_runs`** (the list's live run badges; keyed by `session_id`). `agent_prompts` is deliberately NOT pulled (Stage-3's wholesale slot-replace deletion semantics don't fit the upsert-only puller).
- **Writes are optimistic + local-first.** Rename / pin / hide (`PATCH`), soft-delete (`DELETE`), restore, reorder, and mark-read apply to the LOCAL mirror immediately (so the now-local list reflects the edit with no revert-then-resync flicker) and enqueue the authoritative push to the outbox as an **upsert** — no remote round-trip in the request. A **hard** delete (`?permanent=true` / phantom fallthrough) is rarer and must fully erase the shared copy, so after the local erase it replicates the delete to the remote **synchronously** (`_hard_delete_family` runs on both) rather than via the row-id-keyed outbox. The pusher does also support an `op='delete'` outbox entry (`_delete_row`) as a general capability. Panel local connections get a `busy_timeout` since the file is now written by the backend, the puller, and the panel at once.
- **Remaining remote calls are pooled.** The endpoints still on the authority (tail, related, non-hybrid fallbacks) borrow from a shared **autocommit connection pool** (`pg_portable.connect_viewer_pooled` / `close_viewer_pool`, size via `WEBAGENT_PG_VIEWER_POOL_MIN`/`_MAX`) instead of a fresh handshake each call — with a standalone-connection fallback so it can only ever be faster.
- **Cross-device delete convergence.** Because the panel now reads local, a delete on device A must reach device B's mirror or B shows a ghost. Two gaps were closed: (1) a **soft** delete now bumps `updated_at` on the status flip — session recycle (`db_viewer`) and agent trash/restore (`local.py` `trash_/restore_custom_agent`) — so the watermark puller carries the recycled/trashed/restored state to every device (previously the status changed but the watermark didn't, so peers never pulled it); (2) a **hard** delete of a session or agent now records a **tombstone** (see the sync-engine paragraph) so peers prune it and its transcript. The acting device is instant (sessions are local-first; agents live-update via the `agent_deleted`/`agent_trashed` WS event); a peer converges within a sync tick (~1–5 s). Corner case: if a peer has the deleted session OPEN and mid-turn, its push-only interactions attach to a row the authority no longer has (orphaned on the remote) and the tombstone pulls the session out from under the open chat on that peer's next tick.

## Agent template + prompt tables (three-way split)

| Table | Job |
|-------|-----|
| **`agent_templates`** | Per-template config (model, temperature, loop_logic, trigger). Seeded from `data/agents/*.json`. |
| **`agent_prompt_templates`** | Canonical slot content per template. Each row keyed by `(template_id, slot_name)`. Carries `version` (int, declared in JSON) + `source` (`'json'` \| `'admin'`). JSON re-seed never overwrites `source='admin'` rows. |
| **`agents`** | Per-user agent instances. References a `template_id`. |
| **`agent_prompts`** | Per-agent runtime slot rows: admin-base rows cloned from `agent_prompt_templates` at agent creation, plus optional per-user overrides (`user_id` set). Each cloned row stamps `template_version`. |

## Seeder lifecycle

`_seed_agent_templates_from_json_files` runs at **app boot only** (and on admin "Re-Seed" button click). Manifest hash of the JSON files is stored in `app_meta.last_agent_manifest_hash`; the seeder short-circuits when the hash matches, so boot stays fast.

Per-slot upsert rules:
- Missing → INSERT with `source='json'`, `version=<JSON version>`.
- Existing `source='json'` AND JSON version > DB version → UPDATE + bump.
- Existing `source='admin'` → SKIP unless `force=True`.

The destructive `DELETE` from the old seeder is GONE. Admin edits in `agent_prompt_templates` survive re-seed unless the admin clicks **Force Re-Seed** in the config page.

The `agent_templates` **config row** (not the prompt slots) is always upserted from the JSON, including the `discoverable` flag. So a template's `discoverable: true/false` in `data/agents/*.json` is authoritative and re-asserted on every re-seed — it controls whether the template appears in the Agents page **"Create a new agent"** dropdown (the dropdown queries `discoverable_only=true`). An admin's runtime discoverable toggle therefore holds only until the next re-seed of changed JSON; to permanently hide/show a template, edit its JSON.

## Dedicated logs store — `logs.db` + `recordings.db` (always local)

Operational logs are a high-volume, **per-machine** firehose that nobody reads across instances, so they live in their **own SQLite files** — separate from the main DB (`local.db` *or* remote Postgres) — managed by **`app/db/logs_store.py`** (`get_log_store()`). Two reasons:

1. **No writer contention with user data.** SQLite allows one writer per *file*. Keeping the log firehose out of the file that holds `interactions` means a burst of log writes can never stall a user-facing write, and vice-versa. This is the "split WAL" — each file has its own WAL and its own `asyncio` write lock.
2. **Logs stay local even when the main DB is remote.** You debug one instance at a time; logging belongs on the box that produced it. The store is SQLite-file-based regardless of the main backend.

| File | Tables | Holds |
|------|--------|-------|
| **`data/db/logs.db`** | `diagnostics`, `tool_executions` | Server-side flight recorder + structured tool metrics |
| **`data/db/recordings.db`** | `render_recordings` | Browser-side render recorder (big HTML blobs; off by default) |
| `data/db/instance_id.txt` | — | A per-box id, created once, stamped on every record |

All three are **gitignored runtime artifacts** (recreated on first run). The optimizer's temp `.db` scratch files are a third, pre-existing local split.

### `diagnostics` table (in `logs.db`)

Backs the flight-recorder (`app/agent/diagnostics.py`) — a rolling, auto-pruned log read back by the Admin Tools → Diagnostics page, `GET /api/v1/diagnostics`, and the `read_diagnostics` agent tool.

- **Categories:** `server` (stdlib logs), `http` (4xx/5xx cause), `loop` (pipeline events), `run` / `recovery` (run lifecycle + self-healing), `tool` (tool errors), **`access`** (every HTTP request), **`ws`** (WebSocket connect/subscribe/disconnect).
- **Columns:** `id, ts, level, category, source, message, detail (JSON), session_id, turn_id, agent_id, user_id, interaction_id, session_seq, turn_seq, instance_id, created_at`. The **correlation keys** (`interaction_id` / `session_seq` / `turn_seq`) join a log line to the exact `interactions` row by key (not by fuzzy timestamp); `instance_id` names the box. `session_id` / `agent_id` are **plain TEXT (not foreign keys)**.
- **Capture level:** the stdlib→recorder handler runs at **INFO** by default (`DIAGNOSTICS_CAPTURE_LEVEL`), with a per-logger policy — our `app.*` loggers at INFO+, noisy third-party libs at WARNING+. Records at/above `diagnostics_persist_level` (INFO default) persist to `logs.db`; below stays in the RAM ring + `logs/*.log` text files. Retention defaults: 200k rows / 168h.
- **Store methods:** `insert_diagnostics_batch`, `query_diagnostics`, `prune_diagnostics`, `clear_diagnostics`.

### `tool_executions` table (in `logs.db`)

Structured per-call metrics (revived from `app/tools/tracker.py`): `tool_name, success, duration_ms, error_type, error_message, input_params, output_preview` + the correlation keys. Filled automatically by the loop tap (pairs each `tool_call` with its `tool_result` and times it) or explicitly via `app.tools.tracker.track_execution(...)`. Sortable/aggregatable by duration & success — unlike the free-text `tool` diagnostics category.

### Correlating logs to interactions

Both stores are local SQLite, so the reader can **`ATTACH`** `logs.db` to the main connection and join `diagnostics`/`tool_executions` to `interactions` on `interaction_id` (or `session_seq`/`turn_seq`). On a single-box device both files share one clock, so timestamp alignment is also reliable — but the keys are the robust join.

> **Note:** the legacy `diagnostics` / `render_recordings` tables still defined in `schema/tables.py` + `local.py` `SCHEMA_SQL` are now **dormant** (the live recorders write to the dedicated store instead). They are left in place to avoid disturbing the Postgres reconciliation path; existing rows simply age out.
